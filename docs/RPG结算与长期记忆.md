# RPG 回合结算与长期记忆

RPG 沿用小说侧分项结算、生成前基线、明确删除和原文取证的机制，同时保留引擎对按钮动作、道具、移动和数值边界的控制。

## 一轮如何完成

1. 自动存档保存行动之前的状态。
2. 引擎先执行明确的动作和移动，更新目的地与在场人物，再生成剧情。
3. 为本轮保存引擎执行后的独立结算基线，以及原始在场名单、对话模式、时间和对应玩家消息。
4. 从本回合完整正文抽取变化，不再只读取最后 3000 字符。模型逐项核对地点与在场人物、数值、背包、人物、处境、长期记忆，并提供连续原文依据。
5. 先检查格式、人物身份、登记地点、入口条件、数量与关联事件。有缺失或冲突时，仅补充核对一次；仍不完整的项目保留待核对状态。
6. 按关联组应用有效变化，一并保存实际前后值和分项结果。物品交接的背包与人物持有状态共同通过或共同保留原值。可选记忆或建议失败不撤销无关联的有效变化。
7. 根据最终地点与人物位置重算在场名单、标记相识，下一轮使用更新后的状态。历史消息的在场名单保持原始见证范围，抵达后的新人物不会因此获得整段此前私聊。

## 玩家看到什么

每段 GM 剧情下显示结算是否完成、简短变化，以及可展开的分项结果和长期事件原文。结算失败时剧情仍保留。尚未完成且有安全基线的最新回合提供“仅重新结算”。

修改 GM 正文后显示待结算提示，并清除可能引用旧正文的滚动摘要。旧版存档中的消息没有独立结算基线时，需要使用原有回滚重玩功能，不能直接猜测并累加旧效果。

## 重试与修订

- 同一正文已经成功结算时，重复请求返回已保存结果，不再次调用模型，也不再次增加物品或扣除数值。
- 部分失败时，保留已通过项目，仅补齐失败项目；应用仍从同一基线计算。
- 正文修订后，从引擎执行后的基线重新计算，因此不会再次执行引擎扣费。
- 此后人工改过的字段受保护；自动重新结算不能覆盖这些修改。
- 后面已有消息、时间已经推进，或人物已被手动移动到别处时，不允许直接重写当前状态。使用对应玩家消息的回滚重玩处理后续依赖。
- 修改较早的正文会将后续结算标记为过期，需回滚重玩，避免新剧情继续使用失效状态。
- 模型调用期间的正文或会话变更会使本次写入失效。并发结算由数据库条件更新和回合状态检查保护。
- 流式连接在结算开始后断开，后台继续保存结算结果；刷新可以查看。

`rpg_messages.settlement` 保存基线、正文指纹、尝试次数、模型提议、实际前后值、分项结果及有原文依据的事件。API 只公开核对结果，不返回内部基线。`state_delta` 只包含实际生效字段的最终值；诊断时使用 `settlement.proposed` 和 `settlement.applied` 区分提议与结果。

## 长期事实与知情范围

拜师、救命、结仇、承诺、重大伤亡、物品交接等事件保存在来源消息的结算记录中，独立于滚动摘要。每条记录包含原文、参与者、见证者和公开范围。

长期记忆注入使用消息编号追溯原文。私聊只允许当时对话参与者知情；群聊中仅注入当前参与者都有权知道的事实。公开事件必须有正文中的传播或公告依据，不能仅因模型填了 public 就进入公共大事记。

来源正文修改后，旧事件不再参与回忆；读档删除后续消息时，相应事件也随来源消息消失。普通数值变化保留在结算审计中，不占用长期事实记忆。

## 验证

核心回归位于 `backend/tests/test_rpg_settlement.py`，覆盖完整正文抽取、漏记移动补查、位置与人物同步、重复结算、正文修订、并发重试、人工修改保护、物品交接、入口条件、失败恢复、权限及私聊记忆。

自然语言事件识别仍依赖模型；代码能核对原文是否存在、身份与结构是否有效，并对常见遗漏发出补查，但不能证明任意复杂叙事的语义。无法确认的变化会保留在待核对结果中。
