# 上下文索引增强可行性报告

> 背景：你提出的问题是——"现在是不是索引这方面做得不够好？如果在构建上下文时，能根据用户输入去搜索相关记忆的**完整原文**（段落、实体、角色数据），是不是能增强和前面剧情的连贯性？"
> 
> 本报告只做分析和建议，不改任何代码。

---

## 一句话结论

**索引算法不是短板，"检索对象"才是**——现在能搜到的只有"摘要"，搜不到"原文段落"。你的直觉方向是对的，但三类目标里只有"段落原文"是真缺口，实体和角色数据其实已经是全量注入了。推荐的补法成本很低：把这次刚做好的"回忆取证"两跳检索泛化成常规能力，不需要建任何新索引。

---

## 二、现状盘点：生成一章时，系统能"查"到什么

| 信息          | 怎么查                                   | 查到后注入什么                 | 评价           |
| ----------- | ------------------------------------- | ----------------------- | ------------ |
| 角色          | 名字出现在指令/大纲/上一章里→直接命中；否则向量兜底           | **整张角色卡**（设定+当前状态+完整档案） | 已是全量，不缺      |
| 道具/地点/势力/功法 | 同上三段式                                 | **整张状态卡**               | 已是全量，不缺      |
| 伏笔/秘密       | 不检索，按预算全部注入                           | 完整条目                    | 无损，不缺        |
| 关系里程碑       | 不检索，全部注入（本次新增）                        | 完整条目                    | 无损，不缺        |
| 历史剧情        | 混合检索（向量+关键词+精确匹配三路融合）                 | **章节摘要**（每章压到500字）      | ⚠️ 只有摘要，原文丢了 |
| 历史原文段落      | 只有"回忆取证"路径能摸到（本次新增），且仅限回忆关键词触发+走里程碑定位 | 相关章的原文片段                | ⚠️ 覆盖面窄      |

结论很清楚：**实体、角色这两类你担心的"完整原文"，其实早就是完整注入的**——只要名字被提到，整张卡都会进上下文，没有"只给一半"的问题。真正有损的环节只有一个：**历史剧情只剩摘要，原文细节（对话原话、具体动作、场景氛围）在压缩时丢掉了**。

## 三、索引算法本身弱不弱？

不弱。上个月刚把单路向量检索升级成了三路混合检索（向量管语义、BM25 管关键词、4-gram 精确匹配管人名功法名这类专有名词），这正是 2026 年调研里性价比最高的升级项，已经做完了。

所以"搜不准"的空间不大了，剩下的问题是"**搜到了也只能给摘要**"。打个比方：图书馆的检索系统很好用，能准确告诉你答案在哪本书里——但书架上只摆了每本书的内容简介，正文都收进仓库了。

## 四、补原文段落的三个方案

### 方案 A（推荐）：两跳泛化——"摘要定位到章，回读原文捞段"

现在的混合检索命中一条摘要时，**已经知道它来自第几章**（元数据里带着章号）。只要加一步：命中摘要后，顺手把那几章的原文读出来、切成自然段、按相关度挑最相关的 1-2 段，附在摘要后面一起注入。

- **为什么便宜**：这次做"回忆取证"时，切段、选段、预算控制这套零件已经全部写好并测试过了（`_split_paragraphs`、`_rank_paragraphs`），方案 A 就是把这套零件从"仅回忆场景可用"接到常规检索链路上，纯复用。
- **不需要新索引**：第一跳还是走现有摘要检索；第二跳只在命中的 3-6 章原文里就地排序，量很小，纯本地计算，不碰嵌入服务。
- **不需要网络**：完全不依赖嵌入端点（咱们的网络环境里嵌入端点不稳，这点很重要）。
- **成本**：新增 token 开销约 800-1500 字/章（可给它单独一块预算，像回忆取证那样）；生成延迟几乎不变。
- **风险**：捞出来的段落可能不是最相关的——但注入的是**真实原文**，最坏情况是"多给了一段真的旧文"，不会引入编造，无害。

### 方案 B：给全书原文段落建向量索引

把 151 章原文全部切段（约几千段）做嵌入，存进 ChromaDB，检索时直接搜段落。

- **好处**：不依赖"摘要先命中"，理论召回上限更高。
- **代价**：① 嵌入端点在当前网络环境下不稳定，几千段的初次嵌入和每章更新都要过这道坎；② 每次改章/重生成都要重索引对应段落，多一套要维护的同步逻辑；③ ChromaDB 体积明显变大。
- **判断**：属于"收益不确定、维护成本确定"的投入。建议先上方案 A，如果实际使用中发现"摘要没命中导致原文捞不到"的情况真实高频，再考虑升级到 B。**不建议现在做。**

### 方案 C：加重排模型（rerank）

在检索结果后面加一个专门的排序模型精排。2026 年调研里属于"有效但要引入新模型依赖"的项，对目前规模（单本小说几百条摘要）收益有限，**继续观望**。

## 五、建议

1. **做方案 A**：把两跳原文检索从"回忆专用"泛化为常规检索链路，预估半天到一天工作量，绝大部分代码是现成的。
2. **不做方案 B/C**：先让 A 跑起来，观察实际生成里"原文片段有没有被用上、用得对不对"（生成时前端能看到每块上下文的来源，正好可以人工抽查），有数据了再决定要不要加码。
3. 如果做 A，建议同时给它加独立开关和独立预算块（和回忆取证、关系里程碑同款机制），觉得吵可以随时关掉。
