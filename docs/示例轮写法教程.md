# 示例轮（few-shot）写法教程

示例轮是 NovelBot 里控制文风最直接的手段。本文讲清楚它在本项目里的工作机制、正确写法和常见误区。

## 一、它在本项目里是怎么工作的

### 存储与入口

- 存在小说表的 `writer_examples` JSON 列，格式：`[{"user": "...", "assistant": "..."}, ...]`
- 前端在「小说设置抽屉」里编辑；写作预设（writer_preset 的 `examples`）套用时会带入
- 生成时由 orchestrator 读出，传给 writer

### 组装位置

`writer.py` 的 `_build_example_turns` 把每个示例对转成两条**真实消息**（一条 user + 一条 assistant，两端都非空才有效），插在 system 之后、参考资料之前：

```
system（写作要求/风格）
  ↓
示例user① → 示例assistant①   ← 伪造的"历史对话"
示例user② → 示例assistant②
  ↓
user：参考资料（世界观+角色+上章结尾）
assistant："已了解…准备创作"
user：任务+写作方向
```

消息里**没有任何"这是示例"的标记**，模型无法区分真假历史——它看到"我之前这样回复过"，就会延续那个腔调。这是标准的 conversation-style few-shot，比把范文塞进 system 写"请参考"效果好：assistant 角色的示范权重更高，且位置固定能吃 prompt cache。

改写流（批注改稿）同样插入示例轮；DeepSeek 分支会把 system 折叠进末条 user，但示例轮位置不变、照常生效。

### 怎么验证

DevPanel 的 `llm_payload` 事件：`diagnostics.example_turns` 是示例轮数量，`message_roles` / `message_chars` 能看到它们从消息序列第 2 位开始。

## 二、正确写法：剧情节拍 → 成文

few-shot 教给模型的不是"指令格式"，而是 **user→assistant 的映射关系**。本项目的最佳写法：

- **user 侧**：压缩的剧情节拍——一句话写完"谁对谁做什么 + 情绪如何递进"，第三人称、无对白
- **assistant 侧**：这段节拍展开后的完整成文

例：

> user：`{{对方}}掐着{{角色名}}的下巴逼她认错，她从嘴硬到哽咽，最后彻底软下来。`
> assistant：（对应的完整成文段落）

这个格式之所以有效：真实生成时最后一条 user 恰好也是这个形态（章节构思/写作方向就是剧情描述），示例演示的变换（节拍→成文）和实际要做的变换完全同构。

### 细节要点

1. **占位符**：user 侧用 `{{角色名}}`/`{{对方}}` 这类占位符是好做法——避免示例绑定具体人名、防止名字漏进正文。注意占位符是**字面发送**的（代码不做渲染），主流模型都能理解。但 **assistant 侧成文建议用示例专用的具体人名**（和小说角色名错开），避免模型把花括号原样吐进输出。
2. **映射方向要统一**：所有示例对都保持"节拍→成文"一个方向。混入"成文→续写"的对（user 侧本身是完整段落），模型学到的映射就模糊了，可能把写作方向当成要续写的原文。
3. **数量**：3-5 组高质量示例即可，多而平庸反而稀释。
4. **双刃剑**：示例 assistant 里的一切都会被当成"正确示范"照抄——包括没注意到的口癖、滥用的比喻。放进去之前把范文里的坏习惯清干净。

## 三、错误写法：条件规则式示例

❌ 把 user 侧写成规则声明：

> user：`当输入中包含以下词汇或内容：讨好的话语、求饶、道歉`
> assistant：（求饶场景范文）

**这不会按预期生效。** few-shot 的触发靠相似度匹配：模型拿最后一条真实 user（剧情节拍）和示例 user 比对形态。规则声明和剧情描述形态完全不同，永远匹配不上。实际后果是**条件失效、风格泄漏**——范文仍会全局性地渗透风格，但"仅在求饶情节时启用"这个条件不被遵守，求饶腔调可能污染不相干的章节。

正确替代：

1. **实例化示例（推荐）**：把条件"藏"进实例——user 侧写一条**包含**求饶/讨好元素的剧情节拍，assistant 给对应范文。将来写作方向出现类似元素时相似度自然命中；不含这些元素的章节匹配不上、不受污染。
2. **显式条件进 system**：在 writer 自定义系统提示词里写"当写作方向出现求饶/道歉情节时，按如下笔法处理：〔范文〕"。模型对 system 里的 if-then 遵从度远高于伪装成对话的规则。

场景类型不止一种时，各写一组实例对，比一条大而全的规则可靠。

## 四、相似度是怎么"算"的

模型内部**没有检索器在选中某组示例**——影响是注意力的连续加权：越像的示例牵引力越强，所有示例永远有一点全局影响（风格渗透的来源）。"像"发生在表示空间里，分三层，牵引力从强到弱：

1. **独特内容词及近义域（最强）**：低频、指向明确的词（"求饶""告饶""哀求"几乎等价，"求饶"和"求助"则差很远）。
2. **场景动力学**：语义骨架层面的相似——比如"支配/受制关系 + 行为持续施加 + 情绪从对抗滑向屈服的递进弧"。换了具体行为但结构相同的节拍，激活依然很高；词汇沾边但动力学不对（如两情相悦的温存戏），只弱弱继承文风。
3. **格式形态**：压缩节拍体 vs 大段对白式构思。写作方向的形态和示例 user 一致时整体激活高，形态错位则影响下降。

### 实操建议

- 写该类章节的写作方向时，**复用示例里的关键动作词/情绪弧词**，主动拉高注意力权重
- 示例 user 侧写得**越典型越好**——它是这类场景的"原型"，变体都往它身上靠；别把某次特殊情节的细节写进去
- 发现不相干章节被某组示例带偏腔调时，把该示例 user 侧写得更"窄"（加入该场景独有的标记词），收敛辐射范围
