# 检索重排（Rerank）方案

状态：**已实施（2026-07-19）**。落地形态与本方案一致，差异点：候选池无需放宽（RRF 融合前两路各取 top_k×4，头部本就够宽），直接对融合结果前 20 条（`reranker.CANDIDATE_K`）精排；重排在线程池执行避免阻塞事件循环。代码：`backend/app/services/reranker.py` + `context_builder.py` 融合点接入，开关 `context_config.rerank`（默认开），测试 `tests/test_reranker.py`。

---

## 一、要解决的问题

现在的 RAG 历史检索是三路混合（向量 + BM25 + 4-gram）用 RRF **按名次**融合。名次融合的盲区：

- 它不看内容，只看排位——一条在三路里都排第 5 的平庸结果，可能压过在某一路排第 1 的真正相关结果。
- 各路的相关性判断都是"粗"的：向量看整段语义、BM25 看词频，都分辨不出"这条摘要虽然词都对上了，但讲的不是这件事"。

典型失败：写"回到当年比武招亲那段"，向量捞到别的比武章节、BM25 捞到只提了一嘴"招亲"的章节，真正写这件事的那章反而没进 top。

重排 = 在末端加一个"精读裁判"：把 query 和候选摘要**拼在一起**送进小模型，输出成对的相关性分数，用分数精选。

**连带收益**：两跳原文取段（rag_fulltext）依赖"命中了哪几章"，重排选章更准，第二跳回读的原文也跟着更准。这是本方案与方案 A 的复利关系，也是"选错章严重就上重排"这个触发条件的由来。

---

## 二、接入位置（改动很小）

只动 `backend/app/services/relevance_selector.py` 一处：

```
现在：三路检索 → RRF 融合 → 取 top 6 注入
之后：三路检索 → RRF 融合 → 放宽取 top 20 候选 → 重排精选 top 6 注入
```

- 重排对象：章节摘要（每条约 500 字），候选仅 20 条左右，计算量极小。
- 可选二期：两跳取段的段落级排序（`_rank_paragraphs`）也换成重排打分，进一步提升选段质量。一期先只做选章。

## 三、模型选型

| 模型 | 参数量 | 显存(fp16) | 备注 |
|---|---|---|---|
| **BAAI/bge-reranker-v2-m3**（一期推荐） | 5.7 亿 | ~1.2 GB | 经典款，中文强，生态成熟 |
| Qwen/Qwen3-Reranker-0.6B | 6 亿 | ~1.2 GB | 新一代，中文榜单领先，备选 |
| Qwen/Qwen3-Reranker-4B | 40 亿 | ~8 GB | 追求上限才用；短摘要场景提升有限 |

结论：本项目 query 具体（写作指令+大纲）、文档短（500 字摘要），**0.6B 级别足够**。

## 四、硬件已确认（2026-07 评估）

用户机器：RTX 5070 Ti (16GB) + AMD R9 9900X + 48GB 内存。

- 显存占用 1-2 GB，GPU 打分 20 条摘要 <100ms；纯 CPU 兜底也只要 1-3 秒，对生成流程无感。
- 结论：硬件完全不是瓶颈，直接走本地模型路线，**跳过 LLM 裁判和 API 重排两个备选**（API 重排因网络环境不稳被否）。

## 五、实施要点与坑

1. **PyTorch 版本**：5070 Ti 是 Blackwell 架构（sm_120），必须 PyTorch 2.7+ 的 cu128 及以上构建。装错老版本 CUDA 不认卡。（实装：torch 2.11.0+cu128）
2. **模型下载**：走 HuggingFace，本机网络环境需设 `HF_ENDPOINT=https://hf-mirror.com` 镜像。1-2 GB 下载一次后纯本地推理，不再依赖网络——这是本地路线相对 API 路线的最大优势。
2b. **系统代理坑（实装时踩到）**：本机 Windows 注册表系统代理是 `socks4://127.0.0.1:10809`，pip 和 huggingface 库即使没有代理环境变量也会从注册表捡到它并报错。对策：pip 安装加 `NO_PROXY="*"` 环境变量 + 清华镜像；模型加载用 `CrossEncoder(..., local_files_only=True)` 彻底禁止联网检查（已写进 reranker.py）。
3. **依赖体积**：`sentence-transformers` + CUDA 版 torch 约 3-5 GB。一期直接装进后端 venv（个人项目省事优先）；嫌污染可单独 venv 起 localhost 打分服务，后端 HTTP 调用。
4. **懒加载 + 常驻**：模型在首次使用时加载并常驻（模块级单例），避免每章生成都冷启动。
5. **降级路径**：模型加载失败 / torch 未装 / 显存不足时，静默回退到现状（RRF 结果直接取 top 6），不阻断生成。加载状态记一条 warning 日志即可。
6. **独立开关**：沿用 `novel.context_config` 机制加 `rerank` 开关（默认开），与其他区块开关一致。

## 六、代码骨架

```python
# 新文件 backend/app/services/reranker.py
from sentence_transformers import CrossEncoder

_model = None

def _get_model():
    global _model
    if _model is None:
        _model = CrossEncoder("BAAI/bge-reranker-v2-m3", device="cuda")  # 失败时抛异常由调用方降级
    return _model

def rerank(query: str, docs: list[str], top_k: int) -> list[int]:
    """返回按相关性降序的原始下标。"""
    scores = _get_model().predict([(query, d) for d in docs])
    return sorted(range(len(docs)), key=lambda i: scores[i], reverse=True)[:top_k]
```

`relevance_selector` 融合后调用，`try/except` 包裹，异常时用原 RRF 顺序。

## 七、验证方式

- 单测：mock CrossEncoder.predict，验证候选放宽、top_k 截取、异常降级三条路径。
- 效果验证（人工）：在测试小说上，用同一条"呼应早期章节"的写作指令，对比开关重排前后 SSE `context_step` 里"相关历史场景"命中的章节号是否更准。**严禁在真实数据上跑**。

## 八、预期收益

- 业界参照：RAG 失败 73% 错在检索侧；"混合检索+重排"是 2026 生产基线（Anthropic 实验中重排使 top-20 检索失败率降 67%）。
- 本项目具体收益：呼应早期章节时选章更准；两跳原文取段跟着受益；候选池小所以边际成本近乎为零。
