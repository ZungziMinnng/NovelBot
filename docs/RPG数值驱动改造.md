# RPG 模式：从跑团改成数值驱动

状态：**已实施（2026-09-11）**。计划的十一个阶段全部落地，前端类型检查与打包通过。

同日补做的第二轮见第十三节。后端 554 个测试通过。**UI 未经浏览器实测**，手动验收清单见第十一节。

---

## 一、为什么要改

原来的 RPG 是一个 AI 当 GM 临场判断「这事有多难」，然后掷 d20 对抗难度值 —— 那是龙与地下城。但这个项目要做的题材是都市、魔法世界、互动养成，**不一定和冒险有关**。这些类型里推动游戏的根本不是「这次撬锁成不成」，而是数值在动、到了某条线就解锁新东西。

所以骰子是冒险题材的一种调味，不是地基。真正的地基是：

```
玩家做一件事 → 数值变了 → 跨过某条线 → 解锁新内容 → AI 按新状态往下写
```

这一版把地基换成这个循环，骰子降级成一个默认关着的可选项。

另外两个一并解决的界面问题：酒馆和 RPG 两个目录里 157 处写死的深色系色值，在 18 套主题里那 6 套浅色底上等于白底白字；设定页只用屏幕中间一条 896px。

## 二、十二条已定决策（勿反复推翻）

| 问题 | 定论 |
|---|---|
| 判定方式 | **默认关掉**（`check_mode` 默认 `never`），想要的模组自己开 |
| 数值谁算 | 混合：道具/移动/动作按钮走引擎（数字死的，AI 碰不到）；自由行动交给 AI 提议 |
| 数值挂在谁身上 | 玩家一套 + 每个角色各一套关系数值（定义只写一份，所有角色共用） |
| 阈值触发 | 接在世界书的 `trigger_condition` 上，不另开事件表 |
| 行动方式 | 自由打字 + 模组自定义动作按钮，两者并存 |
| 角色卡 | 照抄酒馆卡字段结构，放进 RPG 自己的表，两边互不牵连 |
| 地点 | 真地图：地点之间有连接（双向可通），移动是明确动作，可加进入条件 |
| 游戏类型 | 一个文本字段进提示词，配三套前端预设（都市/魔法/养成） |
| 「在场」只有一个定义 | 地点相同才算在跟前。被提到一句的人这一轮照样注入设定，但**不算见过面**；`role = protagonist` 的主角模板永不算 NPC |
| 时间 | **玩家自己拨的时钟**：模组给时段默认表（如 早/中/晚），建局时可改；只有「结束这个时段」能推动它，**没有每时段行动预算**，模型也只能口头遵守 |
| 对话线 | **每个角色一条独立历史**。线是消息上的一列 `thread_id`（NULL = 场面线），**不建线程表**；线主不在当前地点就整轮拒收输入，历史照常可读 |
| 跨线记忆 | 一条**大事记**注入每一条线。口吻必须是「**已经传开的**事」—— 注入每条线等于所有 NPC 全知，密室里干的事不能进去 |

## 三、数据模型

### 玩家数值

`RpgModule.stat_defs`（JSON 列表）定义，字段：`name` / `initial` / `min` / `max`（null = 无上限）/ `for_check`（能否用于判定）/ `on_zero`（无 / 死亡 / 标记）/ `display`（条 / 数字 / 隐藏）。

局里的值**复用 `RpgSession.attributes` 这一列**，没有新增列 —— 它本来就是「名字→数字」的字典，正是新系统要的形状。Python 属性名改叫 `stats`（`mapped_column("attributes", JSON, ...)`），**数据库列名一个字没动**。

### 关系数值

`RpgModule.relation_stat_defs`（JSON 列表），定义一次，每个角色各持一份。存在 `RpgSession.npc_states`，形状 `{"3": {"好感": 62, "met": true}}`，键是 npc_id 的字符串（名字会改，id 不会）。建局时按定义初始化，单个角色要不一样用 `RpgNpc.initial_state` 覆盖。

`met` 是内部标记，控制首次见面才注入外貌，渲染面板时跳过。**谁算见过面只认「地点相同」**（`rpg_context.here_npcs`）：被提到一句的人这一轮也拿得到设定，但人并没见到，记成见过会让他的外貌永远等不到该出现的那一次。

### 三张新表

- **`rpg_items`**：`name` / `description` / `category` / `usable` / `consumable` / `effects`（数值增减）/ `sort_order`
- **`rpg_locations`**：`name` / `description` / `connections`（**存名字不存 id**，因为 `RpgNpc.location` 本来就是字符串）/ `enter_requires` / `sort_order`
- **`rpg_actions`**：`name` / `prompt_hint` / `effects` / `relation_effects` / `requires` / `needs_target` / `sort_order`

### 统一条件格式

```json
{"stats": {"精力": {"op": "<=", "value": 20}},
 "relations": [{"npc": "赫敏", "stat": "好感", "op": ">=", "value": 50}],
 "flags": ["已经拿到钥匙", "!已经被发现"],
 "items": ["铁钥匙"],
 "slots": ["晚", "!早"],
 "day": {"op": ">=", "value": 3}}
```

语义唯一：**条件是附加约束，全部满足才算数**。`flags` 里 `!` 前缀表示这条不能立着，`slots` 同义。

`slots` / `day` 是第十四节加的时钟门控，有两处必须记住：

- **没设时段的模组里 `slots` 一律判不成立**（返回「这个模组没有设定时段」），不是放行。放行会让「只有晚上开」的门永远开着而作者查不出来 —— 与 `relations` 分支「名字对不上就算不成立」是同一条理由。
- `day` 的形状与 `stats` 的 rule 完全一致（`{op, value}`，默认 `>=`），左值是 `RpgSession.day`。**不要给它另发明一种写法**，作者和编辑器都不用学新东西。

`check_condition(cond, sess, npcs) -> (bool, 原因)` 写在 `services/rpg_state.py`，**三处共用**：世界书 `trigger_condition`、动作按钮 `requires`、地点 `enter_requires`。这是整个设计里最关键的一处复用 —— 写一遍用三次，所以前端的 `ConditionEditor.tsx` 也只有一份。

### 世界书阈值触发

`rpg_world_entries.trigger_condition`（避开 `condition` 这个保留字）。空 = 无条件，同改造前。

- 常驻词条 + 条件 → 满足就每轮注入（「好感过 50 之后她的说话方式变了」）
- 关键词词条 + 条件 → 提到关键词**且**满足条件才注入

好处：不用新建事件表、不用新注入管线、不用新编辑界面。世界书的 `depth` 机制本来就能把内容插到任意位置，事件该有的能力它全有。

## 四、一轮怎么跑

```
玩家输入
 ├─ 点了动作按钮 / 道具「使用」/ 地图某地点 → 请求带 action_id / item_name / move_to
 └─ 自由打字 → 直接走叙事

② 引擎结算已定义的部分（数字死的，AI 碰不到）
   use_item → 查 rpg_items.effects，精确增减
   move     → 查 connections + enter_requires，过了改地点，没过明确拒绝
   action   → 查 rpg_actions.effects / relation_effects

③ （可选，默认关）开了判定 → 成功率判定

④ 装配上下文
   世界书按 关键词 + trigger_condition 双重筛
   在场角色的关系数值进 NPC 块（「赫敏：好感 62/100」）
   已定死的事实夹在玩家那句话的头尾

⑤ 叙事（贵模型，流式）
⑥ 结算（便宜模型，出 JSON）—— 只结算自由行动那部分，引擎算过的明确告知不许再动
⑦ 应用改动 → clamp → 查 on_zero → 存快照
```

**「混合」的落点就在这里**：有定义的东西数字是死的，AI 改不了；没定义的事才让 AI 提议。

## 五、判定：成功率制，默认关闭

`rpg_dice.py` 原地重写（文件名未改），从 d20 对抗换成成功率：

```python
BASE_RATE = {"trivial": 90, "easy": 75, "medium": 55, "hard": 35, "extreme": 15}
成功率 = clamp(BASE_RATE[档位] + (数值 - 10) * 4 + 模组偏移, 5, 95)
```

玩家看到的是「说服　成功率 63%」，不是「D20+2 对抗 16」。

两个开关：`check_mode` 默认 `never`（新模组开箱完全不判定）；`random_check` 默认 true（关掉后变纯数值确定性判定，同一存档重玩结果一样）。

`dc_table` 列复用成成功率表（形状一样），Python 属性名改叫 `rate_table`，列名不动。`dc_ledger` 原样保留 —— 它防的是档位漂移，和换不换算法无关。

## 六、存档回溯

`SNAPSHOT_FIELDS` 一共十二项，**`summary` 和 `summarized_upto_id` 必须跟着一起存**：漏了它们，回溯之后摘要里还留着「未来」的剧情，模型会写出玩家没经历过的事 —— 这是最难查的一类 bug。

> **通则（这条已经被踩到第三次了）：任何「会随回合自己变的」会话列都必须进 `SNAPSHOT_FIELDS`。**
> 漏一个不会报错、不会测试失败，只会让读档之后留下一个不还原的字段。`summary` / `summarized_upto_id` 是第一次，第十四节的 `time_slots` / `slot` / `day` 是第二次。写新列之前先回头看这张表。

**后加进 `SNAPSHOT_FIELDS` 的字段要配一份兜底**（`SNAPSHOT_DEFAULTS`）：本次改动之前存下的老快照里根本没有这些键，读档时会被跳过、当前值留在原地。**只给新增字段补默认，不要给老字段也补** —— 「快照里没有这个键」和「这个键的值是 None」是两回事，给老字段补默认再 `setattr` 到 JSON 列上会炸。

- 自动档每回合在**动任何东西之前**拍一张（有了权威状态就必须能反悔），只留最近 30 张；手动档永不自动清。
- `_take_save` 必须 `copy.deepcopy`：`AsyncSessionLocal` 是 `expire_on_commit=False`，JSON 列存的是引用，本轮还会就地改这些字典。
- **读档会删掉比这张更晚的存档** —— 它们的 `before_message_id` 指向已不存在的消息，留着只会在下次读档时把进度截断在错误的位置。确认框里写明了。

## 七、界面

### 配色

`index.css` 加两个作用域类，套在两个模式的页面根节点：

```css
.mode-tavern { --primary: 330 81% 60%; --primary-foreground: 0 0% 100%; --ring: 330 81% 60%; }
.mode-rpg    { --primary: 258 90% 66%; --primary-foreground: 0 0% 100%; --ring: 258 90% 66%; }
```

然后把 6 种重复写法机械替换：主按钮 → `bg-primary text-primary-foreground`；次级/标签 → `bg-primary/10 text-primary`；选中态 → `bg-primary/15 text-primary border-primary/40`；取消键 → `border-border text-muted-foreground`。

酒馆的粉、RPG 的紫都保住了，色值集中在一处，`--primary-foreground` 保证前景对比。

**语义色（成功绿/失败红）不能走 primary**，改成双基底写法 `text-emerald-700 dark:text-emerald-300`。这是遗留低对比度问题的唯一正确改法 —— 单基底的 `text-emerald-300` 在浅色底上看不见。

### 布局

- 模组设定页：`max-w-4xl` 单列 → `max-w-[1440px]` + `xl:grid-cols-2`。左栏是世界（封面/游戏类型/世界观/开场/叙事风格），右栏是系统（数值/关系数值/动作/道具/地点/角色卡/世界书/判定）。窄屏自动回落单列。
- 游戏页：`max-w-[1600px]`，对话区居中 + 右侧 320px 常驻菜单。

### 游戏页常驻菜单（JRPG 感的关键）

四格 **状态 / 道具 / 地图 / 存档**，宽屏（≥1280px）钉在右侧一直显示，窄屏收成抽屉。

- **状态**：玩家自己（头像/名字/地点 + 每项数值一根横条）→ 每个已知角色一张卡（头像/在不在面前/关系数值横条），点开是全屏角色详情（外貌/性格/分栏档案全摊开）
- **道具**：每件一张卡，效果染色显示（绿 `精力 +30` / 红 `资金 -50`），可用的给「使用」按钮
- **地图**：走不通的灰掉并用红字写明原因
- **存档**：存一个 / 读档 / 删除

改之前这些东西藏在右下角几个 7×7 无标签图标里，而且没道具时按钮整个不出现 —— 那不是 JRPG，JRPG 的状态是常驻在屏幕上的。

## 八、两个坑与一处有意简化

### 坑 1：弹窗被页头遮挡（已修）

`RpgModule.tsx` 的页头是 `sticky top-0 z-20`，`main` 是 `relative z-10`。**`relative z-10` 让 main 成为独立的层叠上下文**，里面的弹窗再怎么调 z 值也只在 main 内部排序 —— 弹窗写的 `z-50` 和页头的 `z-20` 不在同一场比赛里，结果页头压住了弹窗顶部。

修法：`CharacterForm.tsx` 和 `NpcSheet.tsx` 用 `createPortal` 挂到 `document.body`。

**同类风险**：酒馆的开局弹窗（`Tavern.tsx:201`）目前是侥幸没事 —— 它的页头和 main 都是 `z-10`，靠 DOM 顺序才盖得住。哪天给那个页头加 `z-20` 或改成 sticky 就会复现。项目里另外四十来处弹窗都是「写在页面内部 + fixed z-50」的写法，目前大多没踩到只因为父层没起层叠上下文。**新写弹窗一律用 portal。**

### 坑 2：`met` 开局为空（已修）

后端只在角色**真的进过一轮上下文之后**才置 `met`（`rpg_turn.py` 里 `mark_met` 在开流之前调）。所以刚开局那一刻，哪怕 NPC 就站在你的起始地点，侧栏也会写「还没遇到什么人」，动作按钮的对象下拉是空的 —— 第一回合根本没法对她做任何事。

修法：`condition.ts` 里的 `knownNpcs()` 取「见过面的 **或** 此刻在同一地点的」。后端的 `met` 语义没动（它控制的是外貌注入，那个逻辑是对的）。

### 有意简化：没有做自由输入的动作识别

原计划有个 `rpg_action.jinja2`，用便宜模型识别自由打的字属于 `use_item / move / action / free`。**没有实现。** 结构化行动通过请求里的 `action_id` / `item_name` / `move_to` 进来，引擎精确结算；自由打字直接走叙事 + 结算。

**理由**：判定默认关着时，一个普通回合因此只有一次辅助模型调用（结算）而不是两次。「有定义的走引擎」这条决策靠按钮本身就满足了。

**代价**：打字说「我喝下药水」拿到的是 AI 估算的数字，点背包里的「使用」才是精确的 +20。想补上的话就是加这一个模板 + `rpg_turn.py` 里一个分支。

## 九、四列作废但删不掉

`RpgSession.hp` / `hp_max`、`RpgModule.default_attributes` / `default_hp_max`。

项目没有 Alembic，`create_all` 不会删列，而这几列建成了 NOT NULL、默认值只在 Python 侧 —— 从模型里拿掉会让老库插入直接失败。只能留在模型里加注释。要彻底清掉得单独做一次建新表搬数据的迁移，不值得也有风险。

## 十三、第二轮补的三件事（2026-09-11）

对照第一版代码复核时发现的缺口，都补上了。

### 「被提到」不再算「见过面」

`onstage_npcs()` 原本把「被名字或触发词提到的人」和「真的在跟前的人」混成一份名单，`run_turn` 拿它直接 `mark_met()`。两个后果：只在闲聊里被提过一句的角色，等玩家真走到他面前时外貌描写（注入条件就是 `met` 为假）永远不会再发；前端侧栏也会把没见过的人提前列出来。

改法是把「在场」收到唯一一处定义：

- `here_npcs(npcs, location)` —— 只认地点相同的人，`mark_met` 和侧栏读它
- `onstage_npcs(npcs, location, scan_text)` —— 在跟前的人 + 被提到的人，只用来决定这一轮往模型面前摆谁的设定

**关键词召回的行为没变**：被提到的人这一轮照样注入设定。改的只是「注入」和「算见过」从此解耦。`diag` 里因此有了两份名单：`npcs_here`（真的见到了）和 `npcs_onstage`（这一轮发了谁的设定）。

### 主角模板不再被当 NPC

`RpgModule` 里 `role = protagonist` 的那张卡是开局预填玩家自己的，前端一直把它排除在外（`condition.ts` 的 `knownNpcs`），后端却完全没有 role 判断——只要它填了地点或名字出现在对话里，就会被塞进【在场】让模型当成「别人」来演。现在 `world_npcs()` 统一过滤，`onstage_npcs`、`_settle` 的在场名单都走它。

### RPG 提示词设置页

存储层（`User.rpg_prompts` 列、迁移、`rpg_prompts.PROMPTS`/`validate`/`render`）第一版就在，缺的只是写入入口——想改 `rpg_gm.jinja2` 只能改代码。现在有了 `/api/rpg/prompts/`（每用户一份 JSON，互不影响，所以不加 `require_admin`）和 `/rpg/prompts` 页面（入口在 RPG 首页页头）。模板写坏在保存那一刻就报 400，不会等玩家按下回车才炸。

### 「帮我想想」

`rpg_suggest.jinja2` 早就注册好了，但生产路径零调用。现在输入框左边有个灯泡按钮，按需要三条候选行动，点一条直接发出去。

注意它和原有的建议**不是一条路**：每轮结算顺带产出的 `suggestions`（`rpg_settle.jinja2` 的字段 → SSE → 前端 `tips`）仍然照旧，那条是被动等来的；灯泡是主动要的。两者共用前端同一块显示区。

**已知限制，不修**：RPG 没有摘要管线（`maybe_summarize` 只被酒馆调用），`sess.summary` 恒为空、`summarized_upto_id` 恒为 0。所以 `rpg_suggest.jinja2` 的 `summary` 变量当前永远拿不到值（模板里是 `{% if summary %}`，会自动跳过），而且「帮我想想」在长局里只看得到最近 4 个回合。这是「长局失忆」的同一个根因，属于另立项的范围。

### 明确不修

自由打字绕过地图：`apply_state_delta` 直接赋值 `location`，不查 `connections` / `enter_requires`。视为玩家自愿作弊，保留原样。

## 十四、批 A：时段与门控（2026-09-11）

起因是「太像桌面跑团了」。真正的缺口只有一个：**没有时间**。玩家经历的时长全靠模型在叙事里自己编，引擎一无所知，所以世界书写不了「鬼只在晚上出现」、地点写不了「第 3 天才开门」—— 没有任何东西可以按时间门控。

**新增 LLM 调用数 = 0。** 结束时段是纯引擎。这一条是这批能成立的前提。

### 时钟长什么样

- **模组是表的唯一来源**（`RpgModule.time_slots`，如 `["早","中","晚"]`）。
- **这一局只记「我停在第几格」**（`RpgSession.slot` + `day`）。`RpgSession.time_slots` **只在玩家建局时真的改过才非空**，那是这一局的覆盖值，从此冻住不再追溯（理由同 `default_location`）；空 = 跟模组走。
- **为什么不是建局时拷一份**：拷了就等于把局冻住。作者发现「早中晚」该拆成三格、改了模组，已经开的局纹丝不动 —— 这是个几乎必然会踩的坑（实测踩过一次）。「跟模组走」必须是活的。
- **「空」只有一个含义：没见过 / 没定制。** 不表示「这一局不要时钟」。想不要时钟，只能让模组本身不设时段 —— 「单独关掉某一局的时钟」这个能力是有意不要的。
- 判定表用 `slot_table(module, sess)` 一处算出来（`services/rpg_state.py`）：`sess.time_slots or module.time_slots`。
- **`slot` 存的是名字不是下标**。存下标就得把 `module` 传进 `check_condition` 才能换算，那会打破「一处写完、三处共用」（第 68 行那条立身之本）。先例是 `RpgLocation.connections` 也存名字不存 id。
- **推到最后格就翻篇**：回到第一格、`day += 1`、跨天回满。这就是「分幕」。
- **空 `time_slots` = 这个模组不管时间**，按钮不出现，`advance` 什么都不做，一切与加这个字段之前完全一致。老库拿到的默认值就是空。

### 这一批之前开的局怎么拿到时钟

时段是这批新加的列，这批之前开的局拿到的是 `'[]'` 和 `''`，界面上整块时钟都不出现。修法是**只补 `slot`（站到第一格），不碰 `time_slots`**：`database._backfill_rpg_clock()`，挂在已有的启动期幂等修复 `_repair_data()` 后面。

- **不要顺手把模组的表拷进局里**（早期版本就是这么写的，已在 2026-09-11 改掉）。拷一次就把这一局永久冻住，模组后来改对了它也不动 —— 实测踩过，表现是「我明明把时段改成三格了，这一局还是一格、按一下就翻篇」。
- 幂等：补过的局 `slot` 非空，下次启动不再匹配。每次启动都跑，代价是一次 JOIN 查询。
- 纯 Python 而不是写进那串 SQL，是因为要取 JSON 数组的第一个元素，交给 SQL 做要依赖 `json_extract`。
- **`bind` 参数只为测试**：默认那个 `engine` 指向真实数据，测试必须能指到自己的库。

### 逗号 bug 的脏数据

同一个逗号 bug 还留下了一种坏数据：整张时段表存成了一个格子，名字是几格连写（`["早中晚"]`），表现是时钟只有一格、按一下就翻篇。`database._repair_concatenated_clock()` 负责清掉它，判据是精确的：

> 这一局的时段表**只有一格**，且它的名字**正好等于**模组那几格名字的连写。

别的形状一律不碰（玩家自己起的名字不会误伤；模组本来就只有一格时判据不成立），清过一次就不再匹配。修法是丢掉这一局自己那份，退回跟模组走。

**这个函数是临时的**，等确认没有别的库中招就可以删。<br>
注意它**不动 `day`**：天数已经走歪了，但那是真实发生过的按键，没有依据倒推回去，宁可留着。

### 跨天回满

`RpgStatDef.reset_daily`，语义是**回到 `max` 不是回到 `initial`**。「回满」只在有上限时才成立，而且这样绕开了「建局时玩家把初始值改过」的归属问题。没上限的项（资金）跳过。

UI 上这个勾**只出现在 `max` 非空的行**，而且只给玩家数值那一张表（关系数值不需要）。副作用写进已知限制：没上限的项想每天清零做不到，那是另一个字段的事，本批不做。

### 模型那边是软约束

【你】状态块在 `所在：` 后面加一行 `时间：第 2 天 · 晚`（模组没设时段就不加这行 —— 一句 `时间：第 1 天 · ` 比不写更糟，模型会拿这个半截值去编）。`rpg_gm.jinja2` 加一句静态文字禁止「不知不觉天黑了」这类写法。

**这是口头约束，不是机制保证**，模型偶尔仍可能擅自跨时段。堵不住也不想堵：结算 JSON 里压根没有时间字段，模型连提议时间的通道都没有，比「提议了再校验掉」干净。残留风险见下文。

### 一处必须记住的边角

`advance` 和（下一批的）`/move` 都**绕过了 `stream_turn` 里的自动存档**，所以两者都得**自己拍一张自动档**，否则玩家按了时钟 / 瞬移五格再读档，回到的是上一个*回合*，中间的状态变化无法反悔。它们的 `before_message_id` 与上一次回合相同，`restore_save` 会删 0 条消息、只回滚状态 —— 这正是要的。

### 一个踩过的坑：逗号打不进去

时段表、剧情标记、道具都是「一行逗号文本 ↔ 字符串数组」。原先的写法是

```tsx
<input value={list.join('，')} onChange={e => onChange(splitList(e.target.value))} />
```

**这个写法里逗号根本敲不进去。** 你敲下 `，`，onChange 拿到 `"早，"`，`splitList` 切成 `["早"]`，重渲染时 `join` 回 `"早"` —— 那个逗号在这一次往返里被吃掉了。表现是输入框里怎么按逗号都不出现，最后整个时段表存成了一个格子叫「早中晚」。

改成 `rpgUi.CommaInput`：组件自己存一份**原始文本**，只在「外面传进来的值不是我们自己刚发出去的那一份」时才覆盖输入框（用 `useRef` 记住上一次发出的值）。这个判断是必须的 —— 少了它，打字过程本身就会触发上面那个覆盖。

`flags` / `items` 两栏从一开始就有同样的 bug，一并换掉了。中英文逗号、顿号、分号都认。

### 已知限制（不修，接受）

1. **跨时段是软约束。** 模型可能仍写「你花了一整个下午」。前端不拦，因为拦不了 —— 没有一个可靠信号。
2. **建局后改了时段名，老局会停在旧名字上。** `advance_slot` 的处理是从第一格重新数起、且**不加一天**（名字对不上不等于过了一天）。有测试钉住。
3. **已被用户覆盖过的 `rpg_gm.jinja2` 拿不到那句新提示。** 这是每用户覆盖的固有代价，有先例，接受。
4. **没上限的数值不能跨天清零。** 见上。

## 十五、批 B：分线对话、大事记、地点总览（2026-09-11）

批 A 解决了「没有时间」，这批解决「只有一个对话框」。两个真实缺口：

1. 所有对话挤在一条消息流里，跟酒馆和铁匠的聊天首尾相接。想跟某个人单独待一会儿，就得跟全体角色的上下文抢窗口；想「回到酒馆接着上次聊」，引擎也不知道「上次」是哪一段。
2. 分线之后必然出现的失忆：**「你在铁匠铺听说老兵他哥失踪了，回去找老兵，老兵没听过」**。摘要器修不了这个 —— 摘要只管一条线。

**新增 LLM 调用数 = 0。** 瞬移、结束时段、列对话线都是纯引擎和查询；大事记复用已有的那次结算调用。这条是批 A、批 B 共用的前提。

### 线是消息上的一列，不是一张表

最初的设计是建 `rpg_threads` 表（每个角色一条线）。**最终没有建**：`rpg_messages` 上加一列 `thread_id`（可空），**NULL 就是场面线**。

玩家看到的行为完全一样 —— 每个角色一条独立历史，各自记录、各自保存、互不干扰，进谁的门看谁的对话。差别只在实现形状，换来三件很实在的事：

1. **老数据零回填。** 这批之前的所有局，消息的 `thread_id` 全是 NULL，它们**自动变成一条完整的场面线**，一个字都不用回填（也就绕开了「逐局先插行再回填」这种写不进那串静态 SQL 的逻辑）。
2. **回溯不会有幽灵线。** 读档是按消息 id 全局删。线如果是消息的派生结果，删完自动一致；如果是一张独立的表，读档后会留下一堆「未来才创建的空对话」，还得再写清理、挂到删会话和删模组两处级联上。
3. **不需要摘要器。** 独立线程表的意义主要在于挂「每线程一条摘要指针」—— 那正是酒馆那套会互相打架的机制。不做这张表就顺带绕开了整个问题。

代价：角色被删之后前端拿不到名字，只能显示兜底文案。将来真要做「每线程一条摘要」得再加表，但那时消息上的 `thread_id` 已经是现成的分组键，是拎出来不是重做。

**命名**：列名和请求参数都叫 `thread_id`，但它的**值是 NPC 的 id**。名字表达的是概念（「这是哪条对话线」），不是外键指向（不建表就没有外键）。不叫 `npc_id` 是因为那会和已有的 `target_npc` 在同一个请求体里撞车，读代码的人一定会混。这两件事的区分贯穿整批：

- `thread_id` 决定**这段叙事去哪条历史**
- `target_npc` 决定**好感加在谁头上**（`relation_effects`）

在老兵线里对老板娘用动作是合法的。

**两件绝对不能做的事**（不会报错，也不会被现有测试发现）：

- 不给 `thread_id` 加外键或 `ON DELETE SET NULL`
- 不把 `npc_id` 写进 `database._repair_data` 的悬空外键清理

两者都会把一条角色线**静默变成场面线，两条历史当场合并**。

### 大事记：口吻必须是「已经传开的事」

跨线记忆靠一条全局大事记（`RpgSession.chronicle`，JSON 列表，上限 40，超了砍最早的，比照 `FLAG_LIMIT`）。**但这里有个陷阱，是本批最要紧的一条**：大事记注入每一条线，等于所有 NPC 全知 —— 你在密室里干的事，隔着半个镇子的老兵也会「知道」。

所以口吻和字段说明一起定死：

- 块名【外场】，开头一句固定话术：「以下是这一带已经传开的事。人尽皆知的传闻，不等于每个人亲眼见过 —— 谁在场、谁只是听说，按各自的位置来。」
- 结算模板里的字段说明写「只有**值得让所有人都知道、且已经传开**的事才写，只有你或少数人知道的事一律不写」。

这样「铁匠铺听说老兵他哥失踪」能跨线（那确实是公开消息），「你半夜翻进他家」不会。

**两个写入者，都不额外花 LLM 调用：**

- **模型写**（叙事性事件）：`rpg_settle.jinja2` 的输出 JSON 加 `chronicle` 字段，`_settle` 按 `suggestions` 的同款做法读出来，非空才追加。
- **引擎写**（确定性事件）：**移动写，但和上一条移动合并** —— 不合并的话玩家在镇上连点五个地点，大事记全是「你去了 X」，真正传开的那件事被挤出去。**时段推进不写**（时钟噪音同理），**只在跨天那一格写一行**，这样换个地点还能知道过了几天。

**注入位置**：【在场】之后、**【世界设定】之前**。理由是整块截断从尾部切：大事记是「已经发生过的硬事实」，和状态同类；【世界设定】【叙事样例】【此前剧情】各有自己的上限、是可牺牲的。放最后的话一旦超预算，被切掉的正好是跨线记忆 —— 那正是它存在的理由。预算 800 token，`truncate_to_token_budget(..., keep_end=True)` 保新弃旧。

**结算能看到最近 10 条**，只为防它把同一件事反复写进去，不是让它接着往下编。

### 一轮归哪条线

前端每次都显式传 `thread_id`。后端只在 `rpg_turn.resolve_thread_id` **一处**解析：传了就用传的（认不出来算场面线），没传但 `target_npc` 在场就归他，否则场面线。

**引擎行动的归属**：移动、用道具一律落**场面线**（它们不是对话）；带 `needs_target` 的动作落被选角色的线 —— 前端在点的时候主动把线切过去，不让后端猜。

**输入门控在后端强判**：线主不在当前地点就**整轮拒掉**（400「你得先回到铁匠铺」），历史照常可读，只是不给输入框。不拒的话线和历史就不再一一对应，之后每个查询都要考虑「线主不在这儿」的分支 —— 堵在入口比散在各处便宜。前端的表达是地点页只列**当前地点**的人。

**新增【当前线】一行**（约 15 token）：场面线写「此刻没有特定的对象，这是公共场面」，角色线写「你正在与『老兵』单独说话」。挡的是「线开了但模型仍把在场三人写成一锅粥」，顺带把「场面线承载群戏」这个语义写进提示词。

### `_settle` 的三处收窄

1. **`allow_move` 开关。** `apply_state_delta` 原本会写 `location`（第十三节明确保留的「自由打字绕过地图」）。分线后这会变成**看得见的 bug**：在老兵线里被叙述走到别处 → 老兵不在了 → 他的输入框永久置灰。所以**非场面线传 `False`**，并在 warnings 里回一句「这一轮的地点变化被忽略了」。场面线保持原样 —— 这条边界正好画在那个决定上，没有改它。
2. **关系数值的候选从全量收窄成「线主 + 在场的人」**，模型不会给不在场的人乱加数字。
3. **`_store_reply` 带上 `thread_id`**，写进 assistant 行。

**`mark_met` 一个字没改。** 它管的是「外貌只在首次见面注入」，判据是地点相同；从老兵面前走过没说话也算见过他，这是对的。线是另一个概念，不要合并。

### 瞬移：`POST /sessions/{id}/move`

地点总览里点一个地方就直接过去。`rpg_turn.silent_move` 照 `_resolve_engine` 的写法自己开会话、自己算、自己落库，核心**直接复用 `_move()`**（它本来就是纯函数：查双向连接、过 `enter_requires`、改地点、返回一句事实）。走不通就把那句拒绝话原样给玩家（「从 X 没有路直接过去」）—— 拦路是地图的正常反馈，不是错误，不弹红色失败。

**它自己拍一张自动档**（同批 A 的 `advance`，理由见第十四节「一处必须记住的边角」）。

「描述一下路上」是旁边另一个按钮，走完整回合 —— 想要路上的见闻时用它，代价是一次正常的叙事。

**不加线程列表端点**：前端已经取了这一局的全部消息，按 `thread_id` 分组就有线了。少一个端点，也不会出现「新消息不在当前线的查询结果里所以看不到」那一类 bug。代价是长局多传些数据。

### 界面：三级

**总览**（地点卡片网格：点卡身进地点页，「过去」= 瞬移，「路上」= 完整回合）→ **地点页**（这里有谁，点谁进谁的线；另有「大家在一起」进场面线）→ **对话线**（原来那个聊天界面，只显示这条线的消息）。

- 「场面线」的 UI 文案特意**不叫「独处」**：它会膨胀成**公共场面**，三人同桌吃饭、群戏、环境描写都只能落这里。写成「独处」玩家就不知道该把群戏往哪放了。
- 侧栏的**地图那一格撤掉了** —— 它现在是主界面，而且「过去」从「走一个完整回合」变成了纯引擎瞬移，和侧栏其他格子不是一类东西了。
- `openNpc` 从 `StatusSidebar` 提到 `RpgPlay`：地点页也要开同一个角色档案弹窗，只能有一份。
- **SSE 消费逻辑一行没动**（事件形状没变），只是流式气泡额外带上 `thread_id`，这样切线的瞬间它不会挂到别的线上。
- **切线程时 `target` 重置为线主**：不重置就会**跨线泄漏** —— 在老兵线里 `target` 还留着老板娘，下一个动作的好感加到别人头上。场面线一律清空：自动替玩家选一个对象，会把这一轮悄悄送进那个人的线。
- 读档后回总览、回场面线：线是消息的派生结果，消息删回那一刻，当时还不存在的线就没了。
- 诊断行露出的字段从 2 个变成一整排（`state_tokens` / `npc_tokens` / `chronicle_tokens` 本来就发了却没显示）。

### 三条要写进规章的东西

1. **任何随回合变化的会话列都必须进 `SNAPSHOT_FIELDS`。** 这条被 `summary` / `summarized_upto_id` 强调过一次（第六节），批 A 的时钟是第二次，本批的 `chronicle` 是第三次。漏了不报错，只是读档之后那一样东西不还原 —— 最难查的一类 bug。
2. **`sess.summarized_upto_id` 永远不能用来给线切片。** 它是会话级单值（现在恒为 0，所以无害）。将来真做压缩，指针要挪到线上；而且分线之后「全局摘要」这个概念本身就不成立了。另立项，别在这轮顺手把 `sess.summary` 接进线上下文。
3. **新增 LLM 调用数 = 0**，这两批都是。

### 已知限制（不修，接受）

1. **角色被删之后，他那条线显示不出名字。** 线只是消息上的一个 id，没有外键就查不到名字。比建表方案多一行兜底文案。
2. **读档后默认落在总览，不一定是读档前那条线。** 存档不带线名（`label` 只是「第 N 回合」）。
3. **角色线里被叙述走到别处会被忽略**，只在 warning 里说一句。这是有意换来的：否则线主的输入框会永久置灰。
4. **自由打字绕不过线。** 在老兵面前自由打字（不从他的线进）会落在场面线，设计如此。如果这让人困惑，**改界面而不是改逻辑**。
5. **`maybe_summarize` 没有动**，`rpg_summary.jinja2` 继续是死代码。线各自增长比原来的全局转录慢，而 `history_window` 本来就在切片。

## 十六、批 A/B 的回头修置（2026-09-11）

批 A（时段）和批 B（地点总览）落地后的一轮审查 + 真实存档取证，改掉下面这些。

### 1. `/move` 必然死锁（阻塞级）

`silent_move()` 照搬了 `_resolve_engine` 的写法（自己开一个 `AsyncSessionLocal`），而它是被路由直接调用的：路由已经拍了存档，写事务开着，再另开一条连接改 `rpg_sessions` —— SQLite 单写者，必死锁。玩家端的现象是「按一下转满 30 秒（`busy_timeout`）然后报 database is locked」。`_resolve_engine` 本人没事：它跑在 SSE 生成器里，路由那个事务已经提交了。

改法：`silent_move` → `move_by_name(sess, locs, npcs, name)`，纯函数，不开会话不落库；地点表/角色表由路由读好传进去，改动跟路由一起提交。**规章：被路由同步调用的引擎函数不得自己开连接。** 回归测试改成跑真路由 + **文件**数据库（`:memory:` 共用一条连接，根本重现不了，这也是当时测试全绿的原因）。

### 2. 时钟的开关不能看 `sess.slot`

建局之后作者才给模组加时段时，这一局的 `slot` 永远是空（只有建局、`advance_slot`、启动回填会写它），而前端拿 `sess.slot` 当时钟的开关 —— 时钟整块不出现，玩家没任何办法推时段，所有按 `slots` 设门槛的内容被无声锁到下一次重启。现在顶欏和侧欄一律按「有没有时段表」判（`sess.time_slots || module.time_slots`，和后端 `slot_table` 同一条规则），`slot` 空着就只显示天数，按一下落到第一格。

### 3. 自动档灌水

时钟和瞬移不产生消息，所以它们所有快照的 `before_message_id` 都是同一个。真实库里已经攒出 10 张同位置的空档（离 30 张的窗口差一点就把真正的回合档挤掉）。现在 `_take_save` 对 `kind="auto"` 去重：同一个消息位置只留**最早**那张（要回到的就是「这一串点击之前」）；手动档不去重。走不通的瞬移还会把刚拍的那张 `expunge` 掉。

### 4. 点地点卡片打开的是自己待的地方

`onPick(loc.name)` 名字传了，但上游 `onPick={() => setView('place')}` 丢掉了，而地点页画的永远是 `sess.location`。改法：卡身只有「你在这里」那张能点（卡片上本来就写了描述和「这里有谁」，去别处只能用「过去」/「路上」）。

### 5. 道具被「收起来」弄没了

真实存档里取证（`rpg_saves` 逐张对比 + `state_delta`）：结算模型把「把东西锁进自己办公桌抽屉」写成了 `qty: -2`，引擎忺忺执行，玩家的东西就没了（而剧情里还写着它在抽屉里）。不是代码 bug，是提示词没把界画清：`rpg_settle.jinja2` 的 `inventory` 说明现在写明「**只有真的不在手上了才写负数**；收进口袋、藏起来、锁进自己抽屉都不算」。

### 6. 其余

- `go` / `advance` 加 `engineBusy` 防连点（原来两下会发两个请求、各拍一张档）。
- 被拦下来的瞬移不再跳到地点页（以前不论成不成都跳，看着像已经到了）。
- `LocationOverview.faces()` 改用 `knownNpcs()`，不再手写第二份「见过面」的判据。
- `RpgSessionCreate.time_slots` 的注释写反了（它说「空列表 = 不用时段」，而实现/测试/设计都是「空 = 跟模组走」）。

### 还欠的

- `database.py` 的 `_repair_concatenated_clock` 自己写着「这个函数是临时的」，真库启动修过一次之后就可以连测试一起删。
- 刷新页面会回到总览（`view` / `threadId` 不持久化）。
- 自由时间让「跟天回满」等于无限回满：时段只靠玩家按，想回满就按到第二天。要拦只能给每天的行动次数设上限，属于玩法设计，不在这两批里。

## 十七、数值的影响 + RPG 界面重做（2026-09-12）

两件事一起做的，因为它们撞在同一个文件（`StatBar.tsx`）上。

### 一、数值能写「影响」

**问题**：作者定义「好感」只能填名字、初始、上下限、怎么显示。数字本身不带任何意思，模型看到 `好感 62/100` 只能自己猜 62 算高还是低、该用什么态度说话；作者心里那句「好感过 60 她就会替你出头」没有任何地方能写。

**数据形状**（不动列、不动迁移、不动 schema）。两个可选键塞进现有的定义字典：

```json
{"name": "好感", "max": 100, "display": "条",
 "effect": "决定她愿不愿意帮你",
 "tiers": [{"at": 0, "label": "冷淡", "note": "不愿多搭一句话"},
           {"at": 61, "label": "亲近", "note": "会主动替你出头"}]}
```

零改动是能成立的，因为 `stat_defs` / `relation_stat_defs` 是裸 `JSON` 列（`models/rpg.py`），schema 里声明成光秃秃的 `list`，`update_module` 是个无脑 `setattr` 循环，而 `def_map` 把整个字典原样当值返回。新键自动对所有人可见。前端那边 `StatDefsSection` 的 `patch` 和 `genrePresets` 的 `bar()` 都是展开合并，也不抹未知键——已确认没有任何地方逐字段重建定义字典。

**分档只写一个下界 `at`，不写区间。** 匹配 = `at <= 值` 里最大的那个。写成 min/max 区间的话作者能留出空隙和重叠，落进空隙是「没有档」、落进重叠是「两个档」，而且都不报错；单下界让这两件事结构上不可能。编辑器把推出来的区间（`0–20`、`61 以上`）显示出来，作者看到的就是实际生效的。

**模型侧两处改动，都在 `rpg_context.py`：**

1. `_stat_text` 追加当前那一档的**短标签**：`好感 62/100（亲近）`。这个函数是玩家数值和 NPC 关系数值共同的唯一出口，改它一处就够。
2. 新块【数值的含义】整轮只发一次，排在【你】之前，装 `effect` 和每档的 `note`。

**为什么 `note` 不跟在数字后面**：关系定义是全体 NPC 共用的一份，跟在数字后面等于同一句话按在场人数重复。`NPC_TOKEN_BUDGET` 只有 1200，中文按 1.5 token/字算，全体在场角色加起来只有约 800 字，`_npc_block` 的注释已经写了「三个人同框就已经到崖边」。按 3 数值 × 3 人 × 26 字算是 350 token，占掉近三成预算，会提前触发降级阶梯——而阶梯砍到底还超就从尾部切，切掉的是**整整一个人**，同时 `mark_met` 照样把他标成见过，于是那个人的外貌**从此再也不会注入**。共用定义在这里从负担变成优势：说明只发一遍，标签跟着数字走。

**明确不做**：`rpg_settle.jinja2` / `rpg_adjudicate.jinja2` 一个字不动。它们自己内联 `{% for key, value in stats.items() %}`，`relation_names` 收的是一串光名字；把元素从字符串换成字典会让用户存下来的模板覆盖里的 `{{ name }}` 渲染出一个字典，静默坏掉。也不开事件表，「阈值触发接在世界书上」这条既定决策没被推翻——这是渲染时在定义上贴一句话，不是一张表。

### 二、RPG 界面重做

**「扁平」的真正原因不是缺组件库。** 用户记得的那个「插件」确有其事：首个提交 `a147ff8` 的 package.json 带着整套 shadcn（10 个 `@radix-ui/*` + cva + clsx + tailwind-merge），`22c66ed` 把依赖全删了，但**留下了 shadcn 的变量样板**——而样板里 `--card` 和 `--background` 是同一个色。所以「卡片」在默认的两个主题下和页面背景数学上同色，只剩一条 1px 边框。加上 28k 行里只有 51 处 shadow、4 处 gradient、面板标题是 `text-sm`（和正文一样大）。换任何组件库都治不了这个。

**所以改的是变量层和共用件，不重写那 5253 行。**

1. **`--card` 没有动。** 直接掰开它会把整套主题的色相带偏（Monokai 会变成紫灰），而用户明确选了「只改 RPG 那几页」。改成：一切套在 `.mode-rpg` 里——四个 RPG 页面（`Rpg` / `RpgModule` / `RpgPlay` / `RpgPrompts`）本来就都带这个类，另外 26 个页面一个像素不动。
2. **起伏靠阴影，取 `--foreground`**：深色主题下它接近白，落成一圈微光；浅色主题下接近黑，是正常的投影。一条规则两种基底都成立，不用判断明暗，也不用定义阴影 token。
3. **侧栏**：垫一层实心 `--card` 再盖一层 `--foreground` 薄纱（`.rpg-side`）。两层都是实心的，不会透出后面的 Silk 把字压花。
4. **板块色** `--rpg-cast` / `--rpg-bag` / `--rpg-save` / `--rpg-map`，定在 `.mode-rpg` 里，**固定不跟主题走**——换个主题就找不到道具在哪的话，这套辨识度就白做了。落在页眉渐变（`.rpg-head`）和左侧那道 1px 色条上；色条这个手法仓库里本来就有（`Landing.tsx` 顶部，注释自己写着「参考图里区分卡片类型的主要手段」），只是从没在别处用过。
5. **共用件**收进 `rpgUi.tsx` 的 `PANEL` / `ACCENT`：`Section` 加 `accent` 和分层的页眉，标题从 `text-sm` 提到 `text-base`；`DeleteButton` 的 `hover:bg-red-50`（浅色主题的写死值，在 18 套深色主题下是一块发光的粉斑）改成双基底写法。侧栏那四张重复的 `rounded-xl border bg-card/70 p-3` 和另外四处同款收敛到 `PANEL`。
6. **`StatBar` 按比例变色**（低玫红 / 中琥珀 / 高翠绿，一律双基底），顺带承载数值影响的档位标签——侧栏的玩家数值、侧栏的 NPC 关系条、角色卡的关系条因此一次全覆盖。`StatePanel` 那个紧凑孪生体共用 `StatBar` 导出的 `bandOf`，免得同一个数字在两处显示得不一样。

**注意**：`--rpg-*` 这些变量定义在 `.mode-rpg` 这个 div 上。`createPortal` 到 `document.body` 的东西（`NpcSheet`、`ConfirmDialog`）**不在**这棵子树里，拿不到这些变量——所以它们没有套 `PANEL`。以后要把哪个弹窗改成 `PANEL` 或 `ACCENT`，得先把变量挪到 `:root` 或者给弹窗根节点补上 `mode-rpg`。
