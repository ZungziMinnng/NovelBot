# RPG 模式：从跑团改成数值驱动

状态：**已实施（2026-09-11）**。计划的十一个阶段全部落地，前端类型检查与打包通过。

同日补做的第二轮见第十三节。后端 554 个测试通过。**UI 未经浏览器实测**，手动验收清单见第十一节。

---

## 一、为什么要改

原来的 RPG 是一个 AI 当 GM 临场判断「这事有多难」，然后掷 d20 对抗难度值 —— 那是龙与地下城。但这个项目要做的题材是都市、魔法世界、互动养成，**不一定和冒险有关**。这些类型里推动游戏的根本不是「这次撬锁成不成」，而是数值在动、到了某条线就解锁新东西。

所以骰子是冒险题材的一种调味，不是地基。真正的地基是：

```
玩家做一件事 → 数值变了 → 跨过某条线 → 解锁新内容 → AI 按新状态往下写
```

这一版把地基换成这个循环，骰子降级成一个默认关着的可选项。

另外两个一并解决的界面问题：酒馆和 RPG 两个目录里 157 处写死的深色系色值，在 18 套主题里那 6 套浅色底上等于白底白字；设定页只用屏幕中间一条 896px。

## 二、十二条已定决策（勿反复推翻）

| 问题 | 定论 |
|---|---|
| 判定方式 | **默认关掉**（`check_mode` 默认 `never`），想要的模组自己开 |
| 数值谁算 | 混合：道具/移动/动作按钮走引擎（数字死的，AI 碰不到）；自由行动交给 AI 提议 |
| 数值挂在谁身上 | 玩家一套 + 每个角色各一套关系数值（定义只写一份，所有角色共用） |
| 阈值触发 | 接在世界书的 `trigger_condition` 上，不另开事件表 |
| 行动方式 | 自由打字 + 模组自定义动作按钮，两者并存 |
| 角色卡 | 照抄酒馆卡字段结构，放进 RPG 自己的表，两边互不牵连 |
| 地点 | 真地图：地点之间有连接（双向可通），移动是明确动作，可加进入条件 |
| 游戏类型 | 一个文本字段进提示词，配三套前端预设（都市/魔法/养成） |
| 「在场」只有一个定义 | 地点相同才算在跟前。被提到一句的人这一轮照样注入设定，但**不算见过面**；`role = protagonist` 的主角模板永不算 NPC |
| 时间 | **玩家自己拨的时钟**：模组给时段默认表（如 早/中/晚），建局时可改；只有「结束这个时段」能推动它，**没有每时段行动预算**，模型也只能口头遵守 |
| 对话线 | **每个角色一条独立历史**。线是消息上的一列 `thread_id`（NULL = 场面线），**不建线程表**；线主不在当前地点就整轮拒收输入，历史照常可读 |
| 跨线记忆 | 一条**大事记**注入每一条线。口吻必须是「**已经传开的**事」—— 注入每条线等于所有 NPC 全知，密室里干的事不能进去 |

## 三、数据模型

### 玩家数值

`RpgModule.stat_defs`（JSON 列表）定义，字段：`name` / `initial` / `min` / `max`（null = 无上限）/ `for_check`（能否用于判定）/ `on_zero`（无 / 死亡 / 标记）/ `display`（条 / 数字 / 隐藏）。

局里的值**复用 `RpgSession.attributes` 这一列**，没有新增列 —— 它本来就是「名字→数字」的字典，正是新系统要的形状。Python 属性名改叫 `stats`（`mapped_column("attributes", JSON, ...)`），**数据库列名一个字没动**。

### 关系数值

`RpgModule.relation_stat_defs`（JSON 列表），定义一次，每个角色各持一份。存在 `RpgSession.npc_states`，形状 `{"3": {"好感": 62, "met": true}}`，键是 npc_id 的字符串（名字会改，id 不会）。建局时按定义初始化，单个角色要不一样用 `RpgNpc.initial_state` 覆盖。

`met` 是内部标记，控制首次见面才注入外貌，渲染面板时跳过。**谁算见过面只认「地点相同」**（`rpg_context.here_npcs`）：被提到一句的人这一轮也拿得到设定，但人并没见到，记成见过会让他的外貌永远等不到该出现的那一次。

### 三张新表

- **`rpg_items`**：`name` / `description` / `category` / `usable` / `consumable` / `effects`（数值增减）/ `sort_order`
- **`rpg_locations`**：`name` / `description` / `connections`（**存名字不存 id**，因为 `RpgNpc.location` 本来就是字符串）/ `enter_requires` / `sort_order`
- **`rpg_actions`**：`name` / `prompt_hint` / `effects` / `relation_effects` / `requires` / `needs_target` / `sort_order`

### 统一条件格式

```json
{"stats": {"精力": {"op": "<=", "value": 20}},
 "relations": [{"npc": "赫敏", "stat": "好感", "op": ">=", "value": 50}],
 "flags": ["已经拿到钥匙", "!已经被发现"],
 "items": ["铁钥匙"],
 "slots": ["晚", "!早"],
 "day": {"op": ">=", "value": 3}}
```

语义唯一：**条件是附加约束，全部满足才算数**。`flags` 里 `!` 前缀表示这条不能立着，`slots` 同义。

`slots` / `day` 是第十四节加的时钟门控，有两处必须记住：

- **没设时段的模组里 `slots` 一律判不成立**（返回「这个模组没有设定时段」），不是放行。放行会让「只有晚上开」的门永远开着而作者查不出来 —— 与 `relations` 分支「名字对不上就算不成立」是同一条理由。
- `day` 的形状与 `stats` 的 rule 完全一致（`{op, value}`，默认 `>=`），左值是 `RpgSession.day`。**不要给它另发明一种写法**，作者和编辑器都不用学新东西。

`check_condition(cond, sess, npcs) -> (bool, 原因)` 写在 `services/rpg_state.py`，**三处共用**：世界书 `trigger_condition`、动作按钮 `requires`、地点 `enter_requires`。这是整个设计里最关键的一处复用 —— 写一遍用三次，所以前端的 `ConditionEditor.tsx` 也只有一份。

### 世界书阈值触发

`rpg_world_entries.trigger_condition`（避开 `condition` 这个保留字）。空 = 无条件，同改造前。

- 常驻词条 + 条件 → 满足就每轮注入（「好感过 50 之后她的说话方式变了」）
- 关键词词条 + 条件 → 提到关键词**且**满足条件才注入

好处：不用新建事件表、不用新注入管线、不用新编辑界面。世界书的 `depth` 机制本来就能把内容插到任意位置，事件该有的能力它全有。

## 四、一轮怎么跑

```
玩家输入
 ├─ 点了动作按钮 / 道具「使用」/ 地图某地点 → 请求带 action_id / item_name / move_to
 └─ 自由打字 → 直接走叙事

② 引擎结算已定义的部分（数字死的，AI 碰不到）
   use_item → 查 rpg_items.effects，精确增减
   move     → 查 connections + enter_requires，过了改地点，没过明确拒绝
   action   → 查 rpg_actions.effects / relation_effects

③ （可选，默认关）开了判定 → 成功率判定

④ 装配上下文
   世界书按 关键词 + trigger_condition 双重筛
   在场角色的关系数值进 NPC 块（「赫敏：好感 62/100」）
   已定死的事实夹在玩家那句话的头尾

⑤ 叙事（贵模型，流式）
⑥ 结算（便宜模型，出 JSON）—— 只结算自由行动那部分，引擎算过的明确告知不许再动
⑦ 应用改动 → clamp → 查 on_zero → 存快照
```

**「混合」的落点就在这里**：有定义的东西数字是死的，AI 改不了；没定义的事才让 AI 提议。

## 五、判定：成功率制，默认关闭

`rpg_dice.py` 原地重写（文件名未改），从 d20 对抗换成成功率：

```python
BASE_RATE = {"trivial": 90, "easy": 75, "medium": 55, "hard": 35, "extreme": 15}
成功率 = clamp(BASE_RATE[档位] + (数值 - 10) * 4 + 模组偏移, 5, 95)
```

玩家看到的是「说服　成功率 63%」，不是「D20+2 对抗 16」。

两个开关：`check_mode` 默认 `never`（新模组开箱完全不判定）；`random_check` 默认 true（关掉后变纯数值确定性判定，同一存档重玩结果一样）。

`dc_table` 列复用成成功率表（形状一样），Python 属性名改叫 `rate_table`，列名不动。`dc_ledger` 原样保留 —— 它防的是档位漂移，和换不换算法无关。

## 六、存档回溯

`SNAPSHOT_FIELDS` 一共十二项，**`summary` 和 `summarized_upto_id` 必须跟着一起存**：漏了它们，回溯之后摘要里还留着「未来」的剧情，模型会写出玩家没经历过的事 —— 这是最难查的一类 bug。

> **通则（这条已经被踩到第三次了）：任何「会随回合自己变的」会话列都必须进 `SNAPSHOT_FIELDS`。**
> 漏一个不会报错、不会测试失败，只会让读档之后留下一个不还原的字段。`summary` / `summarized_upto_id` 是第一次，第十四节的 `time_slots` / `slot` / `day` 是第二次。写新列之前先回头看这张表。

**后加进 `SNAPSHOT_FIELDS` 的字段要配一份兜底**（`SNAPSHOT_DEFAULTS`）：本次改动之前存下的老快照里根本没有这些键，读档时会被跳过、当前值留在原地。**只给新增字段补默认，不要给老字段也补** —— 「快照里没有这个键」和「这个键的值是 None」是两回事，给老字段补默认再 `setattr` 到 JSON 列上会炸。

- 自动档每回合在**动任何东西之前**拍一张（有了权威状态就必须能反悔），只留最近 30 张；手动档永不自动清。
- `_take_save` 必须 `copy.deepcopy`：`AsyncSessionLocal` 是 `expire_on_commit=False`，JSON 列存的是引用，本轮还会就地改这些字典。
- **读档会删掉比这张更晚的存档** —— 它们的 `before_message_id` 指向已不存在的消息，留着只会在下次读档时把进度截断在错误的位置。确认框里写明了。

## 七、界面

### 配色

`index.css` 加两个作用域类，套在两个模式的页面根节点：

```css
.mode-tavern { --primary: 330 81% 60%; --primary-foreground: 0 0% 100%; --ring: 330 81% 60%; }
.mode-rpg    { --primary: 258 90% 66%; --primary-foreground: 0 0% 100%; --ring: 258 90% 66%; }
```

然后把 6 种重复写法机械替换：主按钮 → `bg-primary text-primary-foreground`；次级/标签 → `bg-primary/10 text-primary`；选中态 → `bg-primary/15 text-primary border-primary/40`；取消键 → `border-border text-muted-foreground`。

酒馆的粉、RPG 的紫都保住了，色值集中在一处，`--primary-foreground` 保证前景对比。

**语义色（成功绿/失败红）不能走 primary**，改成双基底写法 `text-emerald-700 dark:text-emerald-300`。这是遗留低对比度问题的唯一正确改法 —— 单基底的 `text-emerald-300` 在浅色底上看不见。

### 布局

- 模组设定页：`max-w-4xl` 单列 → `max-w-[1440px]` + `xl:grid-cols-2`。左栏是世界（封面/游戏类型/世界观/开场/叙事风格），右栏是系统（数值/关系数值/动作/道具/地点/角色卡/世界书/判定）。窄屏自动回落单列。
- 游戏页：`max-w-[1600px]`，对话区居中 + 右侧 320px 常驻菜单。

### 游戏页常驻菜单（JRPG 感的关键）

四格 **状态 / 道具 / 地图 / 存档**，宽屏（≥1280px）钉在右侧一直显示，窄屏收成抽屉。

- **状态**：玩家自己（头像/名字/地点 + 每项数值一根横条）→ 每个已知角色一张卡（头像/在不在面前/关系数值横条），点开是全屏角色详情（外貌/性格/分栏档案全摊开）
- **道具**：每件一张卡，效果染色显示（绿 `精力 +30` / 红 `资金 -50`），可用的给「使用」按钮
- **地图**：走不通的灰掉并用红字写明原因
- **存档**：存一个 / 读档 / 删除

改之前这些东西藏在右下角几个 7×7 无标签图标里，而且没道具时按钮整个不出现 —— 那不是 JRPG，JRPG 的状态是常驻在屏幕上的。

## 八、两个坑与一处有意简化

### 坑 1：弹窗被页头遮挡（已修）

`RpgModule.tsx` 的页头是 `sticky top-0 z-20`，`main` 是 `relative z-10`。**`relative z-10` 让 main 成为独立的层叠上下文**，里面的弹窗再怎么调 z 值也只在 main 内部排序 —— 弹窗写的 `z-50` 和页头的 `z-20` 不在同一场比赛里，结果页头压住了弹窗顶部。

修法：`CharacterForm.tsx` 和 `NpcSheet.tsx` 用 `createPortal` 挂到 `document.body`。

**同类风险**：酒馆的开局弹窗（`Tavern.tsx:201`）目前是侥幸没事 —— 它的页头和 main 都是 `z-10`，靠 DOM 顺序才盖得住。哪天给那个页头加 `z-20` 或改成 sticky 就会复现。项目里另外四十来处弹窗都是「写在页面内部 + fixed z-50」的写法，目前大多没踩到只因为父层没起层叠上下文。**新写弹窗一律用 portal。**

### 坑 2：`met` 开局为空（已修）

后端只在角色**真的进过一轮上下文之后**才置 `met`（`rpg_turn.py` 里 `mark_met` 在开流之前调）。所以刚开局那一刻，哪怕 NPC 就站在你的起始地点，侧栏也会写「还没遇到什么人」，动作按钮的对象下拉是空的 —— 第一回合根本没法对她做任何事。

修法：`condition.ts` 里的 `knownNpcs()` 取「见过面的 **或** 此刻在同一地点的」。后端的 `met` 语义没动（它控制的是外貌注入，那个逻辑是对的）。

### 有意简化：没有做自由输入的动作识别

原计划有个 `rpg_action.jinja2`，用便宜模型识别自由打的字属于 `use_item / move / action / free`。**没有实现。** 结构化行动通过请求里的 `action_id` / `item_name` / `move_to` 进来，引擎精确结算；自由打字直接走叙事 + 结算。

**理由**：判定默认关着时，一个普通回合因此只有一次辅助模型调用（结算）而不是两次。「有定义的走引擎」这条决策靠按钮本身就满足了。

**代价**：打字说「我喝下药水」拿到的是 AI 估算的数字，点背包里的「使用」才是精确的 +20。想补上的话就是加这一个模板 + `rpg_turn.py` 里一个分支。

## 九、四列作废但删不掉

`RpgSession.hp` / `hp_max`、`RpgModule.default_attributes` / `default_hp_max`。

项目没有 Alembic，`create_all` 不会删列，而这几列建成了 NOT NULL、默认值只在 Python 侧 —— 从模型里拿掉会让老库插入直接失败。只能留在模型里加注释。要彻底清掉得单独做一次建新表搬数据的迁移，不值得也有风险。

## 十三、第二轮补的三件事（2026-09-11）

对照第一版代码复核时发现的缺口，都补上了。

### 「被提到」不再算「见过面」

`onstage_npcs()` 原本把「被名字或触发词提到的人」和「真的在跟前的人」混成一份名单，`run_turn` 拿它直接 `mark_met()`。两个后果：只在闲聊里被提过一句的角色，等玩家真走到他面前时外貌描写（注入条件就是 `met` 为假）永远不会再发；前端侧栏也会把没见过的人提前列出来。

改法是把「在场」收到唯一一处定义：

- `here_npcs(npcs, location)` —— 只认地点相同的人，`mark_met` 和侧栏读它
- `onstage_npcs(npcs, location, scan_text)` —— 在跟前的人 + 被提到的人，只用来决定这一轮往模型面前摆谁的设定

**关键词召回的行为没变**：被提到的人这一轮照样注入设定。改的只是「注入」和「算见过」从此解耦。`diag` 里因此有了两份名单：`npcs_here`（真的见到了）和 `npcs_onstage`（这一轮发了谁的设定）。

### 主角模板不再被当 NPC

`RpgModule` 里 `role = protagonist` 的那张卡是开局预填玩家自己的，前端一直把它排除在外（`condition.ts` 的 `knownNpcs`），后端却完全没有 role 判断——只要它填了地点或名字出现在对话里，就会被塞进【在场】让模型当成「别人」来演。现在 `world_npcs()` 统一过滤，`onstage_npcs`、`_settle` 的在场名单都走它。

### RPG 提示词设置页

存储层（`User.rpg_prompts` 列、迁移、`rpg_prompts.PROMPTS`/`validate`/`render`）第一版就在，缺的只是写入入口——想改 `rpg_gm.jinja2` 只能改代码。现在有了 `/api/rpg/prompts/`（每用户一份 JSON，互不影响，所以不加 `require_admin`）和 `/rpg/prompts` 页面（入口在 RPG 首页页头）。模板写坏在保存那一刻就报 400，不会等玩家按下回车才炸。

### 「帮我想想」

`rpg_suggest.jinja2` 早就注册好了，但生产路径零调用。现在输入框左边有个灯泡按钮，按需要三条候选行动，点一条直接发出去。

注意它和原有的建议**不是一条路**：每轮结算顺带产出的 `suggestions`（`rpg_settle.jinja2` 的字段 → SSE → 前端 `tips`）仍然照旧，那条是被动等来的；灯泡是主动要的。两者共用前端同一块显示区。

**已知限制，不修**：RPG 没有摘要管线（`maybe_summarize` 只被酒馆调用），`sess.summary` 恒为空、`summarized_upto_id` 恒为 0。所以 `rpg_suggest.jinja2` 的 `summary` 变量当前永远拿不到值（模板里是 `{% if summary %}`，会自动跳过），而且「帮我想想」在长局里只看得到最近 4 个回合。这是「长局失忆」的同一个根因，属于另立项的范围。

### 明确不修

自由打字绕过地图：`apply_state_delta` 直接赋值 `location`，不查 `connections` / `enter_requires`。视为玩家自愿作弊，保留原样。

## 十四、批 A：时段与门控（2026-09-11）

起因是「太像桌面跑团了」。真正的缺口只有一个：**没有时间**。玩家经历的时长全靠模型在叙事里自己编，引擎一无所知，所以世界书写不了「鬼只在晚上出现」、地点写不了「第 3 天才开门」—— 没有任何东西可以按时间门控。

**新增 LLM 调用数 = 0。** 结束时段是纯引擎。这一条是这批能成立的前提。（二十五章给勾了「外场简报」的模组加了一次可选调用，**默认关**，所以这句话对没勾的模组仍然逐字为真。）

### 时钟长什么样

- **模组是表的唯一来源**（`RpgModule.time_slots`，如 `["早","中","晚"]`）。
- **这一局只记「我停在第几格」**（`RpgSession.slot` + `day`）。`RpgSession.time_slots` **只在玩家建局时真的改过才非空**，那是这一局的覆盖值，从此冻住不再追溯（理由同 `default_location`）；空 = 跟模组走。
- **为什么不是建局时拷一份**：拷了就等于把局冻住。作者发现「早中晚」该拆成三格、改了模组，已经开的局纹丝不动 —— 这是个几乎必然会踩的坑（实测踩过一次）。「跟模组走」必须是活的。
- **「空」只有一个含义：没见过 / 没定制。** 不表示「这一局不要时钟」。想不要时钟，只能让模组本身不设时段 —— 「单独关掉某一局的时钟」这个能力是有意不要的。
- 判定表用 `slot_table(module, sess)` 一处算出来（`services/rpg_state.py`）：`sess.time_slots or module.time_slots`。
- **`slot` 存的是名字不是下标**。存下标就得把 `module` 传进 `check_condition` 才能换算，那会打破「一处写完、三处共用」（第 68 行那条立身之本）。先例是 `RpgLocation.connections` 也存名字不存 id。
- **推到最后格就翻篇**：回到第一格、`day += 1`、跨天回满。这就是「分幕」。
- **空 `time_slots` = 这个模组不管时间**，按钮不出现，`advance` 什么都不做，一切与加这个字段之前完全一致。老库拿到的默认值就是空。

### 这一批之前开的局怎么拿到时钟

时段是这批新加的列，这批之前开的局拿到的是 `'[]'` 和 `''`，界面上整块时钟都不出现。修法是**只补 `slot`（站到第一格），不碰 `time_slots`**：`database._backfill_rpg_clock()`，挂在已有的启动期幂等修复 `_repair_data()` 后面。

- **不要顺手把模组的表拷进局里**（早期版本就是这么写的，已在 2026-09-11 改掉）。拷一次就把这一局永久冻住，模组后来改对了它也不动 —— 实测踩过，表现是「我明明把时段改成三格了，这一局还是一格、按一下就翻篇」。
- 幂等：补过的局 `slot` 非空，下次启动不再匹配。每次启动都跑，代价是一次 JOIN 查询。
- 纯 Python 而不是写进那串 SQL，是因为要取 JSON 数组的第一个元素，交给 SQL 做要依赖 `json_extract`。
- **`bind` 参数只为测试**：默认那个 `engine` 指向真实数据，测试必须能指到自己的库。

### 逗号 bug 的脏数据

同一个逗号 bug 还留下了一种坏数据：整张时段表存成了一个格子，名字是几格连写（`["早中晚"]`），表现是时钟只有一格、按一下就翻篇。`database._repair_concatenated_clock()` 负责清掉它，判据是精确的：

> 这一局的时段表**只有一格**，且它的名字**正好等于**模组那几格名字的连写。

别的形状一律不碰（玩家自己起的名字不会误伤；模组本来就只有一格时判据不成立），清过一次就不再匹配。修法是丢掉这一局自己那份，退回跟模组走。

**这个函数是临时的**，等确认没有别的库中招就可以删。<br>
注意它**不动 `day`**：天数已经走歪了，但那是真实发生过的按键，没有依据倒推回去，宁可留着。

### 跨天回满

`RpgStatDef.reset_daily`，语义是**回到 `max` 不是回到 `initial`**。「回满」只在有上限时才成立，而且这样绕开了「建局时玩家把初始值改过」的归属问题。没上限的项（资金）跳过。

UI 上这个勾**只出现在 `max` 非空的行**，而且只给玩家数值那一张表（关系数值不需要）。副作用写进已知限制：没上限的项想每天清零做不到，那是另一个字段的事，本批不做。

### 模型那边是软约束

【你】状态块在 `所在：` 后面加一行 `时间：第 2 天 · 晚`（模组没设时段就不加这行 —— 一句 `时间：第 1 天 · ` 比不写更糟，模型会拿这个半截值去编）。`rpg_gm.jinja2` 加一句静态文字禁止「不知不觉天黑了」这类写法。

**这是口头约束，不是机制保证**，模型偶尔仍可能擅自跨时段。堵不住也不想堵：结算 JSON 里压根没有时间字段，模型连提议时间的通道都没有，比「提议了再校验掉」干净。残留风险见下文。

### 一处必须记住的边角

`advance` 和（下一批的）`/move` 都**绕过了 `stream_turn` 里的自动存档**，所以两者都得**自己拍一张自动档**，否则玩家按了时钟 / 瞬移五格再读档，回到的是上一个*回合*，中间的状态变化无法反悔。它们的 `before_message_id` 与上一次回合相同，`restore_save` 会删 0 条消息、只回滚状态 —— 这正是要的。

### 一个踩过的坑：逗号打不进去

时段表、剧情标记、道具都是「一行逗号文本 ↔ 字符串数组」。原先的写法是

```tsx
<input value={list.join('，')} onChange={e => onChange(splitList(e.target.value))} />
```

**这个写法里逗号根本敲不进去。** 你敲下 `，`，onChange 拿到 `"早，"`，`splitList` 切成 `["早"]`，重渲染时 `join` 回 `"早"` —— 那个逗号在这一次往返里被吃掉了。表现是输入框里怎么按逗号都不出现，最后整个时段表存成了一个格子叫「早中晚」。

改成 `rpgUi.CommaInput`：组件自己存一份**原始文本**，只在「外面传进来的值不是我们自己刚发出去的那一份」时才覆盖输入框（用 `useRef` 记住上一次发出的值）。这个判断是必须的 —— 少了它，打字过程本身就会触发上面那个覆盖。

`flags` / `items` 两栏从一开始就有同样的 bug，一并换掉了。中英文逗号、顿号、分号都认。

### 已知限制（不修，接受）

1. **跨时段是软约束。** 模型可能仍写「你花了一整个下午」。前端不拦，因为拦不了 —— 没有一个可靠信号。
2. **建局后改了时段名，老局会停在旧名字上。** `advance_slot` 的处理是从第一格重新数起、且**不加一天**（名字对不上不等于过了一天）。有测试钉住。
3. **已被用户覆盖过的 `rpg_gm.jinja2` 拿不到那句新提示。** 这是每用户覆盖的固有代价，有先例，接受。
4. **没上限的数值不能跨天清零。** 见上。

## 十五、批 B：分线对话、大事记、地点总览（2026-09-11）

批 A 解决了「没有时间」，这批解决「只有一个对话框」。两个真实缺口：

1. 所有对话挤在一条消息流里，跟酒馆和铁匠的聊天首尾相接。想跟某个人单独待一会儿，就得跟全体角色的上下文抢窗口；想「回到酒馆接着上次聊」，引擎也不知道「上次」是哪一段。
2. 分线之后必然出现的失忆：**「你在铁匠铺听说老兵他哥失踪了，回去找老兵，老兵没听过」**。摘要器修不了这个 —— 摘要只管一条线。

**新增 LLM 调用数 = 0。** 瞬移、结束时段、列对话线都是纯引擎和查询；大事记复用已有的那次结算调用。这条是批 A、批 B 共用的前提。（同上，二十五章那次可选调用默认关。）

### 线是消息上的一列，不是一张表

最初的设计是建 `rpg_threads` 表（每个角色一条线）。**最终没有建**：`rpg_messages` 上加一列 `thread_id`（可空），**NULL 就是场面线**。

玩家看到的行为完全一样 —— 每个角色一条独立历史，各自记录、各自保存、互不干扰，进谁的门看谁的对话。差别只在实现形状，换来三件很实在的事：

1. **老数据零回填。** 这批之前的所有局，消息的 `thread_id` 全是 NULL，它们**自动变成一条完整的场面线**，一个字都不用回填（也就绕开了「逐局先插行再回填」这种写不进那串静态 SQL 的逻辑）。
2. **回溯不会有幽灵线。** 读档是按消息 id 全局删。线如果是消息的派生结果，删完自动一致；如果是一张独立的表，读档后会留下一堆「未来才创建的空对话」，还得再写清理、挂到删会话和删模组两处级联上。
3. **不需要摘要器。** 独立线程表的意义主要在于挂「每线程一条摘要指针」—— 那正是酒馆那套会互相打架的机制。不做这张表就顺带绕开了整个问题。

代价：角色被删之后前端拿不到名字，只能显示兜底文案。将来真要做「每线程一条摘要」得再加表，但那时消息上的 `thread_id` 已经是现成的分组键，是拎出来不是重做。

**命名**：列名和请求参数都叫 `thread_id`，但它的**值是 NPC 的 id**。名字表达的是概念（「这是哪条对话线」），不是外键指向（不建表就没有外键）。不叫 `npc_id` 是因为那会和已有的 `target_npc` 在同一个请求体里撞车，读代码的人一定会混。这两件事的区分贯穿整批：

- `thread_id` 决定**这段叙事去哪条历史**
- `target_npc` 决定**好感加在谁头上**（`relation_effects`）

在老兵线里对老板娘用动作是合法的。

**两件绝对不能做的事**（不会报错，也不会被现有测试发现）：

- 不给 `thread_id` 加外键或 `ON DELETE SET NULL`
- 不把 `npc_id` 写进 `database._repair_data` 的悬空外键清理

两者都会把一条角色线**静默变成场面线，两条历史当场合并**。

### 大事记：口吻必须是「已经传开的事」

跨线记忆靠一条全局大事记（`RpgSession.chronicle`，JSON 列表，上限 40，超了砍最早的，比照 `FLAG_LIMIT`）。**但这里有个陷阱，是本批最要紧的一条**：大事记注入每一条线，等于所有 NPC 全知 —— 你在密室里干的事，隔着半个镇子的老兵也会「知道」。

所以口吻和字段说明一起定死：

- 块名【外场】，开头一句固定话术：「以下是这一带已经传开的事。人尽皆知的传闻，不等于每个人亲眼见过 —— 谁在场、谁只是听说，按各自的位置来。」
- 结算模板里的字段说明写「只有**值得让所有人都知道、且已经传开**的事才写，只有你或少数人知道的事一律不写」。

这样「铁匠铺听说老兵他哥失踪」能跨线（那确实是公开消息），「你半夜翻进他家」不会。

**两个写入者，都不额外花 LLM 调用：**

- **模型写**（叙事性事件）：`rpg_settle.jinja2` 的输出 JSON 加 `chronicle` 字段，`_settle` 按 `suggestions` 的同款做法读出来，非空才追加。
- **引擎写**（确定性事件）：**移动写，但和上一条移动合并** —— 不合并的话玩家在镇上连点五个地点，大事记全是「你去了 X」，真正传开的那件事被挤出去。**时段推进不写**（时钟噪音同理），**只在跨天那一格写一行**，这样换个地点还能知道过了几天。

**注入位置**：【在场】之后、**【世界设定】之前**。理由是整块截断从尾部切：大事记是「已经发生过的硬事实」，和状态同类；【世界设定】【叙事样例】【此前剧情】各有自己的上限、是可牺牲的。放最后的话一旦超预算，被切掉的正好是跨线记忆 —— 那正是它存在的理由。预算 800 token，`truncate_to_token_budget(..., keep_end=True)` 保新弃旧。

**结算能看到最近 10 条**，只为防它把同一件事反复写进去，不是让它接着往下编。

### 一轮归哪条线

前端每次都显式传 `thread_id`。后端只在 `rpg_turn.resolve_thread_id` **一处**解析：传了就用传的（认不出来算场面线），没传但 `target_npc` 在场就归他，否则场面线。

**引擎行动的归属**：移动、用道具一律落**场面线**（它们不是对话）；带 `needs_target` 的动作落被选角色的线 —— 前端在点的时候主动把线切过去，不让后端猜。

**输入门控在后端强判**：线主不在当前地点就**整轮拒掉**（400「你得先回到铁匠铺」），历史照常可读，只是不给输入框。不拒的话线和历史就不再一一对应，之后每个查询都要考虑「线主不在这儿」的分支 —— 堵在入口比散在各处便宜。前端的表达是地点页只列**当前地点**的人。

**新增【当前线】一行**（约 15 token）：场面线写「此刻没有特定的对象，这是公共场面」，角色线写「你正在与『老兵』单独说话」。挡的是「线开了但模型仍把在场三人写成一锅粥」，顺带把「场面线承载群戏」这个语义写进提示词。

### `_settle` 的三处收窄

1. **`allow_move` 开关。** `apply_state_delta` 原本会写 `location`（第十三节明确保留的「自由打字绕过地图」）。分线后这会变成**看得见的 bug**：在老兵线里被叙述走到别处 → 老兵不在了 → 他的输入框永久置灰。所以**非场面线传 `False`**，并在 warnings 里回一句「这一轮的地点变化被忽略了」。场面线保持原样 —— 这条边界正好画在那个决定上，没有改它。
2. **关系数值的候选从全量收窄成「线主 + 在场的人」**，模型不会给不在场的人乱加数字。
3. **`_store_reply` 带上 `thread_id`**，写进 assistant 行。

**`mark_met` 一个字没改。** 它管的是「外貌只在首次见面注入」，判据是地点相同；从老兵面前走过没说话也算见过他，这是对的。线是另一个概念，不要合并。

### 瞬移：`POST /sessions/{id}/move`

地点总览里点一个地方就直接过去。`rpg_turn.silent_move` 照 `_resolve_engine` 的写法自己开会话、自己算、自己落库，核心**直接复用 `_move()`**（它本来就是纯函数：查双向连接、过 `enter_requires`、改地点、返回一句事实）。走不通就把那句拒绝话原样给玩家（「从 X 没有路直接过去」）—— 拦路是地图的正常反馈，不是错误，不弹红色失败。

**它自己拍一张自动档**（同批 A 的 `advance`，理由见第十四节「一处必须记住的边角」）。

「描述一下路上」是旁边另一个按钮，走完整回合 —— 想要路上的见闻时用它，代价是一次正常的叙事。

**不加线程列表端点**：前端已经取了这一局的全部消息，按 `thread_id` 分组就有线了。少一个端点，也不会出现「新消息不在当前线的查询结果里所以看不到」那一类 bug。代价是长局多传些数据。

### 界面：三级

**总览**（地点卡片网格：点卡身进地点页，「过去」= 瞬移，「路上」= 完整回合）→ **地点页**（这里有谁，点谁进谁的线；另有「大家在一起」进场面线）→ **对话线**（原来那个聊天界面，只显示这条线的消息）。

- 「场面线」的 UI 文案特意**不叫「独处」**：它会膨胀成**公共场面**，三人同桌吃饭、群戏、环境描写都只能落这里。写成「独处」玩家就不知道该把群戏往哪放了。
- 侧栏的**地图那一格撤掉了** —— 它现在是主界面，而且「过去」从「走一个完整回合」变成了纯引擎瞬移，和侧栏其他格子不是一类东西了。
- `openNpc` 从 `StatusSidebar` 提到 `RpgPlay`：地点页也要开同一个角色档案弹窗，只能有一份。
- **SSE 消费逻辑一行没动**（事件形状没变），只是流式气泡额外带上 `thread_id`，这样切线的瞬间它不会挂到别的线上。
- **切线程时 `target` 重置为线主**：不重置就会**跨线泄漏** —— 在老兵线里 `target` 还留着老板娘，下一个动作的好感加到别人头上。场面线一律清空：自动替玩家选一个对象，会把这一轮悄悄送进那个人的线。
- 读档后回总览、回场面线：线是消息的派生结果，消息删回那一刻，当时还不存在的线就没了。
- 诊断行露出的字段从 2 个变成一整排（`state_tokens` / `npc_tokens` / `chronicle_tokens` 本来就发了却没显示）。

### 三条要写进规章的东西

1. **任何随回合变化的会话列都必须进 `SNAPSHOT_FIELDS`。** 这条被 `summary` / `summarized_upto_id` 强调过一次（第六节），批 A 的时钟是第二次，本批的 `chronicle` 是第三次。漏了不报错，只是读档之后那一样东西不还原 —— 最难查的一类 bug。
2. **`sess.summarized_upto_id` 永远不能用来给线切片。** 它是会话级单值（现在恒为 0，所以无害）。将来真做压缩，指针要挪到线上；而且分线之后「全局摘要」这个概念本身就不成立了。另立项，别在这轮顺手把 `sess.summary` 接进线上下文。
3. **新增 LLM 调用数 = 0**，这两批都是。

### 已知限制（不修，接受）

1. **角色被删之后，他那条线显示不出名字。** 线只是消息上的一个 id，没有外键就查不到名字。比建表方案多一行兜底文案。
2. **读档后默认落在总览，不一定是读档前那条线。** 存档不带线名（`label` 只是「第 N 回合」）。
3. **角色线里被叙述走到别处会被忽略**，只在 warning 里说一句。这是有意换来的：否则线主的输入框会永久置灰。
4. **自由打字绕不过线。** 在老兵面前自由打字（不从他的线进）会落在场面线，设计如此。如果这让人困惑，**改界面而不是改逻辑**。
5. **`maybe_summarize` 没有动**，`rpg_summary.jinja2` 继续是死代码。线各自增长比原来的全局转录慢，而 `history_window` 本来就在切片。

## 十六、批 A/B 的回头修置（2026-09-11）

批 A（时段）和批 B（地点总览）落地后的一轮审查 + 真实存档取证，改掉下面这些。

### 1. `/move` 必然死锁（阻塞级）

`silent_move()` 照搬了 `_resolve_engine` 的写法（自己开一个 `AsyncSessionLocal`），而它是被路由直接调用的：路由已经拍了存档，写事务开着，再另开一条连接改 `rpg_sessions` —— SQLite 单写者，必死锁。玩家端的现象是「按一下转满 30 秒（`busy_timeout`）然后报 database is locked」。`_resolve_engine` 本人没事：它跑在 SSE 生成器里，路由那个事务已经提交了。

改法：`silent_move` → `move_by_name(sess, locs, npcs, name)`，纯函数，不开会话不落库；地点表/角色表由路由读好传进去，改动跟路由一起提交。**规章：被路由同步调用的引擎函数不得自己开连接。** 回归测试改成跑真路由 + **文件**数据库（`:memory:` 共用一条连接，根本重现不了，这也是当时测试全绿的原因）。

### 2. 时钟的开关不能看 `sess.slot`

建局之后作者才给模组加时段时，这一局的 `slot` 永远是空（只有建局、`advance_slot`、启动回填会写它），而前端拿 `sess.slot` 当时钟的开关 —— 时钟整块不出现，玩家没任何办法推时段，所有按 `slots` 设门槛的内容被无声锁到下一次重启。现在顶欏和侧欄一律按「有没有时段表」判（`sess.time_slots || module.time_slots`，和后端 `slot_table` 同一条规则），`slot` 空着就只显示天数，按一下落到第一格。

### 3. 自动档灌水

时钟和瞬移不产生消息，所以它们所有快照的 `before_message_id` 都是同一个。真实库里已经攒出 10 张同位置的空档（离 30 张的窗口差一点就把真正的回合档挤掉）。现在 `_take_save` 对 `kind="auto"` 去重：同一个消息位置只留**最早**那张（要回到的就是「这一串点击之前」）；手动档不去重。走不通的瞬移还会把刚拍的那张 `expunge` 掉。

### 4. 点地点卡片打开的是自己待的地方

`onPick(loc.name)` 名字传了，但上游 `onPick={() => setView('place')}` 丢掉了，而地点页画的永远是 `sess.location`。改法：卡身只有「你在这里」那张能点（卡片上本来就写了描述和「这里有谁」，去别处只能用「过去」/「路上」）。

### 5. 道具被「收起来」弄没了

真实存档里取证（`rpg_saves` 逐张对比 + `state_delta`）：结算模型把「把东西锁进自己办公桌抽屉」写成了 `qty: -2`，引擎忺忺执行，玩家的东西就没了（而剧情里还写着它在抽屉里）。不是代码 bug，是提示词没把界画清：`rpg_settle.jinja2` 的 `inventory` 说明现在写明「**只有真的不在手上了才写负数**；收进口袋、藏起来、锁进自己抽屉都不算」。

### 6. 其余

- `go` / `advance` 加 `engineBusy` 防连点（原来两下会发两个请求、各拍一张档）。
- 被拦下来的瞬移不再跳到地点页（以前不论成不成都跳，看着像已经到了）。
- `LocationOverview.faces()` 改用 `knownNpcs()`，不再手写第二份「见过面」的判据。
- `RpgSessionCreate.time_slots` 的注释写反了（它说「空列表 = 不用时段」，而实现/测试/设计都是「空 = 跟模组走」）。

### 还欠的

- `database.py` 的 `_repair_concatenated_clock` 自己写着「这个函数是临时的」，真库启动修过一次之后就可以连测试一起删。
- 刷新页面会回到总览（`view` / `threadId` 不持久化）。
- 自由时间让「跟天回满」等于无限回满：时段只靠玩家按，想回满就按到第二天。要拦只能给每天的行动次数设上限，属于玩法设计，不在这两批里。

## 十七、数值的影响 + RPG 界面重做（2026-09-12）

两件事一起做的，因为它们撞在同一个文件（`StatBar.tsx`）上。

### 一、数值能写「影响」

**问题**：作者定义「好感」只能填名字、初始、上下限、怎么显示。数字本身不带任何意思，模型看到 `好感 62/100` 只能自己猜 62 算高还是低、该用什么态度说话；作者心里那句「好感过 60 她就会替你出头」没有任何地方能写。

**数据形状**（不动列、不动迁移、不动 schema）。两个可选键塞进现有的定义字典：

```json
{"name": "好感", "max": 100, "display": "条",
 "effect": "决定她愿不愿意帮你",
 "tiers": [{"at": 0, "label": "冷淡", "note": "不愿多搭一句话"},
           {"at": 61, "label": "亲近", "note": "会主动替你出头"}]}
```

零改动是能成立的，因为 `stat_defs` / `relation_stat_defs` 是裸 `JSON` 列（`models/rpg.py`），schema 里声明成光秃秃的 `list`，`update_module` 是个无脑 `setattr` 循环，而 `def_map` 把整个字典原样当值返回。新键自动对所有人可见。前端那边 `StatDefsSection` 的 `patch` 和 `genrePresets` 的 `bar()` 都是展开合并，也不抹未知键——已确认没有任何地方逐字段重建定义字典。

**分档只写一个下界 `at`，不写区间。** 匹配 = `at <= 值` 里最大的那个。写成 min/max 区间的话作者能留出空隙和重叠，落进空隙是「没有档」、落进重叠是「两个档」，而且都不报错；单下界让这两件事结构上不可能。编辑器把推出来的区间（`0–20`、`61 以上`）显示出来，作者看到的就是实际生效的。

**模型侧两处改动，都在 `rpg_context.py`：**

1. `_stat_text` 追加当前那一档的**短标签**：`好感 62/100（亲近）`。这个函数是玩家数值和 NPC 关系数值共同的唯一出口，改它一处就够。
2. 新块【数值的含义】整轮只发一次，排在【你】之前，装 `effect` 和每档的 `note`。

**为什么 `note` 不跟在数字后面**：关系定义是全体 NPC 共用的一份，跟在数字后面等于同一句话按在场人数重复。`NPC_TOKEN_BUDGET` 只有 1200，中文按 1.5 token/字算，全体在场角色加起来只有约 800 字，`_npc_block` 的注释已经写了「三个人同框就已经到崖边」。按 3 数值 × 3 人 × 26 字算是 350 token，占掉近三成预算，会提前触发降级阶梯——而阶梯砍到底还超就从尾部切，切掉的是**整整一个人**，同时 `mark_met` 照样把他标成见过，于是那个人的外貌**从此再也不会注入**。共用定义在这里从负担变成优势：说明只发一遍，标签跟着数字走。

**明确不做**：`rpg_settle.jinja2` / `rpg_adjudicate.jinja2` 一个字不动。它们自己内联 `{% for key, value in stats.items() %}`，`relation_names` 收的是一串光名字；把元素从字符串换成字典会让用户存下来的模板覆盖里的 `{{ name }}` 渲染出一个字典，静默坏掉。也不开事件表，「阈值触发接在世界书上」这条既定决策没被推翻——这是渲染时在定义上贴一句话，不是一张表。

### 二、RPG 界面重做

**「扁平」的真正原因不是缺组件库。** 用户记得的那个「插件」确有其事：首个提交 `a147ff8` 的 package.json 带着整套 shadcn（10 个 `@radix-ui/*` + cva + clsx + tailwind-merge），`22c66ed` 把依赖全删了，但**留下了 shadcn 的变量样板**——而样板里 `--card` 和 `--background` 是同一个色。所以「卡片」在默认的两个主题下和页面背景数学上同色，只剩一条 1px 边框。加上 28k 行里只有 51 处 shadow、4 处 gradient、面板标题是 `text-sm`（和正文一样大）。换任何组件库都治不了这个。

**所以改的是变量层和共用件，不重写那 5253 行。**

1. **`--card` 没有动。** 直接掰开它会把整套主题的色相带偏（Monokai 会变成紫灰），而用户明确选了「只改 RPG 那几页」。改成：一切套在 `.mode-rpg` 里——四个 RPG 页面（`Rpg` / `RpgModule` / `RpgPlay` / `RpgPrompts`）本来就都带这个类，另外 26 个页面一个像素不动。
2. **起伏靠阴影，取 `--foreground`**：深色主题下它接近白，落成一圈微光；浅色主题下接近黑，是正常的投影。一条规则两种基底都成立，不用判断明暗，也不用定义阴影 token。
3. **侧栏**：垫一层实心 `--card` 再盖一层 `--foreground` 薄纱（`.rpg-side`）。两层都是实心的，不会透出后面的 Silk 把字压花。
4. **板块色** `--rpg-cast` / `--rpg-bag` / `--rpg-save` / `--rpg-map`，定在 `.mode-rpg` 里，**固定不跟主题走**——换个主题就找不到道具在哪的话，这套辨识度就白做了。落在页眉渐变（`.rpg-head`）和左侧那道 1px 色条上；色条这个手法仓库里本来就有（`Landing.tsx` 顶部，注释自己写着「参考图里区分卡片类型的主要手段」），只是从没在别处用过。
5. **共用件**收进 `rpgUi.tsx` 的 `PANEL` / `ACCENT`：`Section` 加 `accent` 和分层的页眉，标题从 `text-sm` 提到 `text-base`；`DeleteButton` 的 `hover:bg-red-50`（浅色主题的写死值，在 18 套深色主题下是一块发光的粉斑）改成双基底写法。侧栏那四张重复的 `rounded-xl border bg-card/70 p-3` 和另外四处同款收敛到 `PANEL`。
6. **`StatBar` 按比例变色**（低玫红 / 中琥珀 / 高翠绿，一律双基底），顺带承载数值影响的档位标签——侧栏的玩家数值、侧栏的 NPC 关系条、角色卡的关系条因此一次全覆盖。`StatePanel` 那个紧凑孪生体共用 `StatBar` 导出的 `bandOf`，免得同一个数字在两处显示得不一样。

**注意**：`--rpg-*` 这些变量定义在 `.mode-rpg` 这个 div 上。`createPortal` 到 `document.body` 的东西（`NpcSheet`、`ConfirmDialog`）**不在**这棵子树里，拿不到这些变量——所以它们没有套 `PANEL`。以后要把哪个弹窗改成 `PANEL` 或 `ACCENT`，得先把变量挪到 `:root` 或者给弹窗根节点补上 `mode-rpg`。

## 十八、道具定义接进背包（2026-09-12）

**用户报的问题**：「新建模组的时候可以定义道具，但是在游玩的时候没有出现或者说明如何使用」。

**根因不是 bug，是缺一座桥。** 「定义一件道具」（`rpg_items` 表，模组页 › 道具）和「玩家身上有一件道具」（`rpg_sessions.inventory`）是两张表，而建局时**只**把 `rpg_modules.default_inventory` 拷进背包（`api/routes/rpg.py` 的 `create_session`）。`rpg_items` 在那条路上一次都没被读过，两边唯一的联系是**名字字符串**——`_use_item` 按名字去定义里查效果，查不到就发一条「模组里没有「X」这件道具」的 warn。所以作者定义完道具，开局背包仍然是空的。

真实库上的现场（只读查的）：模组「霍格沃茨」有 1 件定义（「校规」），`default_inventory = '[]'`；会话「代理校长」的背包里有 4 件 GM 自己编的东西，一件定义都没有。

### 接法：定义上加一个「开局就带在身上」

新增 `rpg_items.start_with`（`BOOLEAN DEFAULT 0`），建局时和 `default_inventory` **合并**而不是二选一——两者说的不是一件事：`default_inventory` 是「这一局开场凭空多出来的一件东西」（这一局专属的剧情道具），`start_with` 是「这件道具本身就该在玩家身上」（跟着模组走的那几件补给）。合并逻辑是 `rpg_state.starting_inventory(module, items)`，纯函数，好测。

- 认名字用 `norm_name` 而不是字面，撞名时**开局背包那份赢**——它写了数量，比定义默认的一件更具体。没有这条的话，定义里写「治伤药水」、开局背包里写「治伤药水 」（粘贴带了个空格）会给玩家并排显示两条一样的。
- 开局背包的手写行原样搬走（只去掉名字两头的空格），不补字段、不填默认值；定义来的那件带 `qty: 1, note: ""`——侧栏显示说明时本来就先看定义里的 `description`，比手写那栏能写的长。
- **只影响新开的局。** 已经开着的存档不动：给存档补道具等于改玩家正在玩的东西，`default_inventory` 一直也是这个规矩。想让老局也有，只能重开一局。

### 顺带修的两处

1. **预设补上开局道具。** `GenrePreset.items` 现在每条自己声明 `consumable` 和 `start_with`，套用预设的循环**不再写死** `consumable: true`。原来的写法会把「古旧笔记」（关键道具）和「项圈」（装备）也变成用一次就少一个——撕掉的那几页和刻了字的项圈不该消失。规则：预设里的消耗品一律 `consumable: true, start_with: true`（补给是开局就该有的），装备和关键道具两样都是 `false`（要去找到的、戴上就一直在）。
2. **`consumable` 默认跟着分类走。** 编辑器的分类下拉一改，就把「用一次就少一个」跟着设成 `category === '消耗品'`。原来 `EMPTY` 表单把 `consumable` 写死成 `true`，和分类完全无关，所以新建一件「装备」默认也是消耗品。**只给默认值，不锁死勾**——作者仍然可以手改，不然「一瓶反复喝的药水」这种写法就被堵死了。编辑已有道具时不动它：老库里那件 `装备 + consumable=1` 的「校规」打开编辑不会被悄悄改掉。

### 验证

- `test_rpg_state.py` 加了 `StartingInventoryTests`（7 条），全套后端 **683 通过**（原 676）。
- `tsc --noEmit` 干净，`vite build` 成功。
- 迁移在 `/tmp` 的**库副本**上试过（WAL 库必须用 `sqlite3.backup()` 拷，直接 `cp` 会丢掉最近提交，`rpg_items` 整张表都不在）：第一次应用成功，第二次报 `duplicate column name` 被 `_is_expected_migration_error` 吞掉——和其余 ALTER 一个机制。真库只以只读方式打开过。
- 在副本上跑了一遍 `init_db()` + ORM 读写 + `starting_inventory` 的端到端：`start_with` 存得进读得出，背包拼得对。

### 还欠的

- **没有 UI 上的端到端验证**（本地起服务、真点一遍新建模组 → 勾上 → 开局看背包）。`create_session` 那条接线只有一行三句，但项目里没有路由层的测试习惯（全套都是 service 层），所以这行是靠读代码确认的。
- 作者在「开局背包」里写的名字和任何道具定义都对不上时**没有提示**——这一条用户明确说了不做。

## 十九、玩法类别 / AI 助手 / 画布建点 / 游玩时换模型与总结（2026-09-12）

用户一次提了四件事。四件事互不相干，但都是「做完了却差最后一步」的那类缺口。

### 一、玩法类别（模拟 / 探索冒险 / 经营策略）

**为什么不是改 `genre`。** `genre` 存的是「魔法学院」「现代都市生活」这种**世界长什么样**，它和「这局怎么玩」是两根正交的轴——同一个魔法学院，可以是养成模拟，也可以是探索冒险。所以新加一列 `rpg_modules.play_style`，老库拿到 `'rpg'`，行为和加这列之前**一模一样**。

Out schema 用**裸 `str`** 而不是 `Literal`：老库万一有个空串，Literal 会让读取直接 500；所有消费端都走 `style_label()` / `STYLE_RULES.get(...)`，未知值一律按 `'rpg'` 算。

类别真的改三件事，不是个标签：

1. **进提示词。** `services/rpg_play_style.py` 三段玩法规则，由 `rpg_context` 在 GM 模板之后追加成一个**独立的块**。
   **没有改 `rpg_gm.jinja2` 加变量**——用户可能已经把这个模板自定义存进 `user.rpg_prompts` 了，他们那份不含新占位符，玩法卡会对这些人静默失效。独立块对自定义过模板的人照样生效。
2. **建模组时的默认开关跟着变。** 模拟给三个时段、关随机判定；探索冒险开随机判定、不给时段；经营策略给「上半月/下半月」。**只给默认值，作者随时能改。**
3. **界面只做文案与板块取舍。** 判定区块的出现条件是 `play_style === 'rpg' || check_mode !== 'never'`——后半个条件是必须的，不然一个开着判定的模组改成「模拟」之后，判定还在跑却没有任何地方看得见、关得掉。右栏区块按类别换顺序（实现是「块名 → JSX」的一张表 + 按类别给的顺序 map，右栏 JSX 只存在一份）；空格子里的示例词跟着类别换（`stylePresets.ts`，纯文案）。
   **不做类别专属面板**（SLG 资源总览、模拟日程表）——那要新的数据结构，属于玩法设计不是这次的范围。题材预设也**不**按类别过滤。

### 二、逐字段的「AI 生成 / AI 优化」

照酒馆那套：**不落库、不带实体 id**，前端把这一栏当前的文本和几条参考发过去，后端回一段文字进草稿区，作者改完确认才写回表单。

- 栏位白名单只有一处：`agents/rpg_assist.py` 的 `FIELD_SPECS`（9 个栏位：世界观 / 开场 / GM 规则 / 叙事样例 / 角色的性格·外貌·描述 / 地点描述 / 道具描述）。前端多写一个类型，后端直接 400。
- 用**叙事模型**而不是便宜的 fast——这是写世界观和人设的创作活，便宜模型写出来的作者要全部重写，省下的钱没有意义。
- **不生成 `creator_note`**：它有「永不进 prompt」的硬规矩，为它单开一条生成路径不值当。
- 前端**没有直接 import 酒馆那个 `AssistDraft`**：它把 `border-pink-500/30`、`bg-pink-500/[0.04]` 写死了，在 18 套主题下是一块发光的粉斑。RPG 版用 `PANEL` + `hsl(var(--primary))` 重写了一份，放在 `rpgUi.tsx`。
- 按钮放在输入框**下面**而不是 label 那一行：角色 / 地点 / 道具三处的表单是裸 `<textarea>`，根本没有 label 行可挂。一种样式，一个组件。

### 三、画布上直接建点、连线、断线

全在 `LocationSection.tsx`，`MapCanvas` 的 props 从 2 个加到 5 个。**没有引任何画布库。**

- **双击空白建点**（不是单击——拖节点松手常常落在空白上，单击会满地误建）：落点百分比直接当坐标建一个「新地点」，然后自动把下面的表单打开让作者填名字。占位名必须去重（`新地点 2`…）——`connections` 是**按名字**匹配的，重名会让连接指向歧义。
- **连线要一个独立的小把手**：拖节点已经占了节点的 `mousedown`，不给把手就只能按修饰键，没人会发现。落点用 `elementFromPoint(...).closest('[data-loc-id]')` 查，不按坐标猜最近的——节点挨着时会连错人。连接是无向的，只写在源地点上（`edgePairs` 已去重）。
- **点线断开**：1.5px 的线点不中，所以底下垫一条 `stroke="transparent" strokeWidth={10}` 的粗线当命中区（给 `transparent` 而不是 `none` 才参与命中测试）。断开时**两头都清**——实际数据里常常两头都写着，只删一头线还在。
- **`syncForm` 是必须的**：画布上改了连接、而下面的编辑表单正开着同一个地点时，表单里那份 `connections` 是旧的，它 submit 会把整个 form 铺开发出去，刚连的路会被盖回去。
- **`LocForm` 仍然不含 x/y**（原因见文件头注释），建点走独立的一次 create，坐标仍然只由 `place()` 写。下面的表单**没删**：改名、进入条件、批量看一眼还得靠它。
- 仍然只绑鼠标事件。双击建点在触屏上能用，拖连线不能——说明文字照实写了。

### 四、游玩时换模型，以及把总结真正跑起来

**`rpg_summary.jinja2` 一直是死代码。** 它存在、在 `/rpg/prompts` 里能编辑，但全仓没有任何地方渲染它，`sess.summary` 从来没被写过——也就是说超出上下文窗口的早期剧情**直接丢了**，RPG 没有长期记忆。这次补上。

- **每条线各存一份概要**，不是一份全局的。一份全局概要注入每条线，等于把密室里说的话全文告诉所有 NPC——「大事记只能写已经传开的事」那条规矩禁止的正是这个。新增 `rpg_sessions.thread_summaries` / `thread_upto` 两个 JSON 列（键是角色 id 的字符串）；**场面线（`thread_id` 为 NULL）继续用现有的 `summary` / `summarized_upto_id`**，老库和存档格式一个字节不变。
- **写锁绝不跨 LLM 调用**（`rpg_turn.py` 开头那条铁律）。酒馆的 `maybe_summarize` 是「同一个 session 里读 → 调 LLM → commit」，**不能照抄**。这里拆成：开 session 读 → 关 → 调 LLM → 开 session 写 → 关，结构照 `_settle`。
- 失败只 `logger.exception` 不抛：概要停在旧位置，上下文退化成纯截断，下一轮照样能玩。
- **存档必须跟着改**：`SNAPSHOT_FIELDS` 补了这两列。漏了的话读档不回滚概要，回到过去之后概要里还写着「未来」发生的事。这是这一批最容易漏的一处。
- `history_window` 加了 `thread_id` 参数，**两个调用点一起改**（`build_rpg_messages` 和 `suggest_actions`）——两边各切一次的话窗口边界迟早对不上，这本来就是它当初做成公开函数的原因。
- 新增 `summary_model_ref`，消费端一律写 `module.summary_model_ref or module.fast_model_ref`，老库拿到空串行为不变。它单独拎出来是因为要求不一样：这一段压错了会一路带到局终（下一次总结是在它的基础上接着写的）。
- 游玩页页头加一个「模型」按钮，点开三个下拉（叙事 / 判定与结算 / 总结）。**改的是模组**，同一模组的其他存档跟着变（同酒馆，不加 session 级覆盖列），按钮 title 里写明了。用按钮 + 面板而不是三个裸 select：页头已经挤着时钟、结束时段、主题、菜单。面板**留在树里用 absolute，没有 `createPortal`**——`--rpg-*` 定在 `.mode-rpg` 这个 div 上，portal 到 body 的东西取不到（十八章那条注意事项）。
- 下拉的 value 一律是 `String(entry.id)`（走 `modelSelectValue()`）：非管理员用户 `resolve_model_ref` 只认自己的 `ModelEntry.id`，存 model_id 文本会被拒。

## 二十、一条路都没连的地点会被迷雾永久吃掉（2026-09-12 修）

**用户报的**：在模组里加了几个地点，游玩页的地图上只显示两个。

**这是个死锁，不是显示延迟。** 迷雾是顺着 `connections` 散的（去过的 + 它们的邻居），而移动**不看** `connections`（点一下就过去，后端 `_move` 也不看）。两条规矩单独看都成立，凑在一起对**一条连接都没有的地点**就成了死锁：看不见 → 点不了 → 走不到 → 永远照不亮。它会一辈子停在一个灰点上。

这次「画布上双击建点」上线之后这个坑变得很容易踩：双击建出来的地点 `connections` 就是空的，作者加完进游戏发现它不在，只会以为没存上。（真实库里那个「格兰芬多女生宿舍」正是如此。）

**改法**（`condition.ts::visibleLocations`）：**孤立地点始终可见**。判据和 `mapLayout.edgePairs` 同一套（按 `norm` 配名字，悬空名字不算），所以「地图上画得出线」和「能被点亮」说的是同一件事。顺带把 `linked` 里两处字面 `includes` 换成 `norm` 比较——连接名从别处粘进来多一个空格时，原来会出现「线画着、点却是灰的」。

要藏东西**用进入条件**，不要靠不连线：进入条件至少会把「差什么」写在 title 里，而迷雾里的灰点什么都不说。

**没改的**：连通的地点照常散迷雾（A—B—C—D 站在 A，只亮 A、B）。**已知还剩一种**：两个以上地点互相连成一座「孤岛」、而孤岛和玩家所在的那片图不相连时，整座岛仍然永远看不见——这一类要不要整座亮出来是个玩法取舍（亮出来等于泄露布局），没有一并改。

验证：把 `condition.ts` 用 esbuild 编出来，拿**用户真实库里的那四个地点和那份存档**跑了一遍，四个全亮；另外跑了「一条线都没连的模组」「A—B—C—D 的链」「连接名带空格」三种。`tsc` 干净，`vite build` 成功。**没有在浏览器里点过。**

## 二十一、模型面板被角色栏盖住 / 「赫敏」认不出「赫敏格兰杰」（2026-09-12 修）

一起报来的两个，互相没关系。

### 模型下拉垂到角色栏底下

页头和内容区**都是 `relative z-10`**，而内容区在 DOM 里更靠后。同层级后来者居上，于是页头里那些绝对定位的下拉（模型、主题）一垂到内容区上，就被右边的角色栏盖住了。改法是页头升到 `z-20`——它本来就该比内容高一层。（手机抽屉 `z-40`、portal 出去的弹窗仍在更上面，没被这一下影响。）

顺带修掉自己刚写的一个坑：ModelPicker 原来铺了一层 `fixed inset-0` 的幕布收下拉，**这层幕布只盖得住页头那一条**——页头带 `backdrop-blur-md`，而 `backdrop-filter` 会给 `position: fixed` 的后代当包含块。换成仓库里现成的写法（`ref` + `document` 上的 `mousedown`，同 `ThemePicker`）。面板底色也从 `PANEL` 的 `bg-card/70` 换成实心 `bg-card`：半透明的话下面的聊天文字会透上来，三个下拉根本看不清。另外 `${PANEL}` 后面再跟一个 `bg-card` 是**不可靠的**——两者都设 `background-color`，Tailwind 里赢的是 CSS 源码顺序而不是 class 书写顺序。

### 作者写「赫敏格兰杰」，模型写「赫敏」

结算模型提的 `relations` / `npc_notes` 是**按名字**寻址的（它记不住 id），而 `apply_delta` 原来只按 `norm_name` 全等查表。模型在正文里管人家叫「赫敏」，这条改动就被整条丢掉，还每回合冒一句「找不到赫敏」。

新增 `rpg_state.match_npc(name, npcs)`，放宽只放到「**一头对齐**」为止：全等 → 去掉间隔号（`·•・.-_、,，`）再全等 → 一方是另一方的前缀或后缀。两条闸门是必须的：

- **短的那头至少两个字**（`_MIN_PARTIAL`）。一个「李」能撞上满屋人。
- **必须只对上一个人**，对上两个就算认不出。三个「村民甲/乙/丙」在场时，「村民」宁可落空加一条 warning，也不能把好感悄悄加到甲头上——认不出玩家看得见，认错人谁都看不出来。

间隔号只在人名比对时去掉，**没有塞进 `norm_name`**：背包那边「铁-钥匙」和「铁钥匙」是不是一件东西是另一个问题，别顺手一起改（`_NORMALIZE_TABLE` 是和库存匹配共用的）。

`check_condition` 里那处（以及前端 `condition.ts` 的镜像）**仍然是全等**，故意的：那些名字是作者从下拉里选的，不是模型写的，放宽只会让条件在作者改名后悄悄错判到别人身上。

- `tsc --noEmit` 干净，`vite build` 成功。**z-index 那一处没在浏览器里看过**——层级只能真点。

## 二十二、开场人物（2026-09-12）

**用户报的**：开场白里明明写了那个 NPC 在场，游玩页却没显示他。

**不是 bug，是缺一个入口。** 「在场」在这套引擎里只有一个定义：**角色的常驻地点和玩家当前地点一模一样**（后端 `rpg_context.here_npcs`、前端 `condition.onstage`），而角色在游玩过程中**从不移动**（全仓没有任何地方写 `npc.location`）。所以开场白里写到的人要真的出现，他的常驻地点就得等于模组的起始地点——而那一栏在页面另一半的「角色卡」里，隔着半张屏幕，作者不会去对。对不上的后果不只是侧栏名单里没他：他的性格外貌也不进提示词，私聊也找不到他，模型只能现编。

**改法**：在「故事从哪开始」里、起始地点下面加一格**开场人物**，把角色卡列成一排 chip，勾上就是把这个人的常驻地点写成起始地点，取消就是清空。

- **没有加新字段、没有迁移、没有后端改动。** 它是现有那一栏的快捷入口，不是第二套「在场」判据。多加一个 `opening_npcs` 列会立刻分叉：勾了但常驻地点在别处的人，算在场还是不算？两套判据必然有一套是错的。
- 只读**已保存**的起始地点。表单里那一栏改过还没落库时整格禁用，提示「先点右上角保存」——否则会把人放到一个模组根本不从那儿开局的地名上。
- 取消勾选是**清空**而不是还原成别的地名：勾着的时候那个值本来就是起始地点，没有「别处」可还。
- 主角模板排除在外（同 `world_npcs` / `knownNpcs`）。
- 这一格**立刻生效**（直接 PATCH 角色），和模组表单的「点保存才生效」不一样，提示里写明了。

**已知的小缝**：右边「角色卡」里正开着同一个人的编辑表单时，在这里勾一下再去点那个表单的保存，常驻地点会被表单里的旧值盖回去（同 `LocationSection` 里 `syncForm` 挡的那类问题，这里跨了两个区块，没有一并接线）。

**验证**：`tsc --noEmit` 干净，`vite build` 成功。**没有在浏览器里点过**——勾上之后侧栏是不是立刻多出一个人，得真开一局看。

## 二十三、开场白归哪条线（2026-09-12）

**用户问的**：开场白写的是「校长办公室 + 赫敏」，但点赫敏是一条空白对话，只有进「公共场面」才看得到开场白——这种怎么划分。

### 划分：开场白归场面线，不复制

开场白是**第二人称的旁白**，说的是「你在哪、眼前是什么局面」，不是某个人对你说的话。所以它的归属只有一个答案：**场面线**。

**不复制到每条私聊线**，这一条是硬的：历史按线切、概要也按线存，复制之后每条线各自演化、各自被压成概要，同一段开场白在三条线里会被改写成三件不同的事——而它本来是同一件事。「一份全局概要注入每条线」那条规矩禁止的就是这个方向。

### 但有三道缝要补

1. **玩家第一眼看不到它。** 默认视图是地图总览，开场白在 总览 → 地点 → 公共场面 两层里面。新局（玩家一句话都还没说过）现在**直接落在场面线上**，第一眼就是作者写的那一幕。只在进页面时判一次，之后玩家停在哪一级就是哪一级。
2. **点开一个人是纯空白。** 一条还没开口的私聊线，顶上垫一段**公共场面的最后一段旁白**（新局时正好就是开场白），画成虚线框的灰字并写明「来自公共场面，不算你们说过的话」——不标的话玩家会以为这句是对方说的，接着它回话，而模型那条线里根本没有这段文字。有了自己的历史之后这块就消失。
3. **模型在私聊线里也不知道刚才发生了什么。** 建局时把开场白压一条进**外场（大事记）**，带 `〔开场〕` 前缀、截到 120 字。大事记本来就是跨线共享的那条通道，抬头还写着「传闻不等于亲眼见过」，正好合用；截断是必须的，整段旁白塞进去会常驻吃掉外场那 800 token 的预算。

顺带把编辑页的文案改准了：区块说明写明它是「公共场面」那条线的第一条旁白，`hint` 里加了一句「别把只有一个人知道的事写在这里」——开场白是给所有在场的人看的。

**没有新字段、没有迁移。** 外场是现有的 JSON 列，且早在 `SNAPSHOT_FIELDS` 里，读档会跟着回滚。

- 后端 **722 通过**（原 718）。新增 `OpeningSceneTests` 4 条（跑真实路由建局）：开场白只落一条且 `thread_id` 为 NULL、同时多出一条 `〔开场〕` 大事记、超长开场白被截到上限、没写开场白就既不发消息也不写大事记。

## 二十四、角色按时段摆位（2026-09-12）

**起因**：问「时钟跳转的时候 NPC 会不会自己走动」。查下来是**完全不会**——全仓没有任何地方在运行时写 `npc.location`，也没有作息/日程这个概念，时段只被当成门控条件读（「鬼只在晚上出现」），从来不会把谁挪到哪儿去。

要补上这件事有两种做法，这一步只做便宜的那一半：**作者写死的作息表**（纯数据、零模型调用）。真正让模型自己决定「这段时间他去干了什么」是另一半，先不做。

### 加的是「取值方式」，不是第二条判据

「在场」在这套引擎里**只有一个定义**：他在的地方等于玩家在的地方。这一步没有动这条定义，只是把「他在的地方」从一个常量换成了按时段查表：

```
npc_place(npc, slot) = 作息表[当前时段] 或 npc.location
```

- **当前时段在表里有值就用它，没有就落回常驻地点。** 空值（作者清空某一格）也算没有。
- **没有时段（`slot` 为空）时作息表整个不参与。** 不这么办的话，一个从没配过时钟的模组会因为角色卡里多填了一栏而改变行为。
- 作息表是 `RpgNpc.slot_locations`（JSON，`{"早": "大礼堂", "晚": "寝室"}`）。老库拿到 `'{}'`，`npc_place` 一律返回 `location`——**和加这一列之前逐字一致**。

后端 `rpg_context.npc_place` 与前端 `condition.npcPlace` 是**同一套算法的两份拷贝**，这是既有的形状（`here_npcs` ↔ `onstage` 本来就是镜像）。两边一起改，漏一边的症状是「侧栏里他站在你面前，提示词里却没这个人」。

改动落到的调用点（都在防同一件事：有的地方算他到了、有的地方没算）：

| 位置 | 不一起改会怎样 |
|---|---|
| `rpg_context.here_npcs` | 「在场」的唯一定义，标记见过面也读它 |
| `rpg_context.onstage_npcs` | 注入名单。不跟着改的话，玩家跑去作息表上的地方，他的设定反而不进提示词 |
| `rpg_context._npc_block` 的排序 | 顶着作息表在场的人会被排在「只是被提到」的人后面，进而被挤出 token 预算 |
| `rpg_turn.thread_blocker` | 私聊的门控。不跟着改，人明明在那儿却拒收输入，或者反过来 |
| `rpg_turn.resolve_thread_id` / `_settle` 的名单 | 结算只会给「在场」的人加好感和近况 |
| 前端 `onstage` / `PlacePage` / `LocationOverview` / `StatusSidebar` / `NpcSheet` | 面板上的「就在你面前」和地点上站着谁，会和引擎说的不一致 |

### 编辑页

角色卡里多一栏「作息：哪个时段在哪儿」，时段名来自模组自己的时段表（**没有时段表就整栏不出现**）。角色卡列表、游玩页的侧栏和角色详情一律显示**此刻**在哪儿（`npcPlace` 的结果），不再显示常驻地点——写常驻地点会让玩家跑过去扑空。

**开场人物那一格跟着一起改了**：开局站的是时段表的第一格，所以那张 chip 现在按 `npcPlace(npc, 第一格)` 判定，而不是按常驻地点。作息表把他支到别处时 chip 直接禁用，title 里写明「作息表里『早』写的是 X，要改去角色卡」——不禁用的话，点了会去改常驻地点，而改了对那个时段毫无影响。

## 二十五、推时段时的外场简报（2026-09-12）

上一步补的是「他去哪儿了」，这一步补的是「他在那儿干了什么」。剩下的选项里，让模型真正自由行动太重（要一套跨线的 NPC 状态机），所以先做一个便宜的近似：**推时段时多调一次便宜模型，写一两句「别处此刻在发生什么」进大事记。**

### 这一次调用把既有承诺改了，所以做成开关

「结束这个时段是纯引擎，零 LLM 调用」这句话原先写在三处：路由的 docstring、游玩页按钮的 title、本文档十四章。加了简报之后它对**开着开关的模组**就不成立了。

处理方式不是悄悄改口，是**加 `RpgModule.offscreen_brief` 开关，默认关**：

- 老模组（迁移后拿到 `0`）按一下时钟仍然是零调用，那三句话对它们仍然逐字为真。
- 开了之后按钮 title 会换成「会调一次便宜模型写一句『别处』」，编辑页的勾选框下面也写明「按一下时钟就会花钱、也要等一下」。

### 只写玩家见过的人

简报进的是**大事记**，而大事记注入每一条对话线。所以进了名单的人，之后任何一条线都可以随口提起他。两个闸门：

- **只写 `npc_states` 里 `met` 为真的人**。没见过的人出现，等于让模型知道一个玩家还不该知道的名字（同「没见过的不该被抖出来」那条既有规矩）。
- **只写他此刻按作息表所在的地方**（`npc_place`），prompt 里把地点直接给定，不许挪动他。

名单为空（都在玩家身边、或一个都还没见过）时**直接返回，连模型都不叫**——大多数局的头几轮都是这样。

### 防编造

模版 `rpg_offscreen.jinja2` 里逐条写死：不许出现新的人名、地名、组织名、物品名；不写对白；不写玩家的行动；不写「有人来杀你、东西被偷」这类会立刻改变玩家处境的大事；没内容可写就输出「无」。

引擎侧还有三道兜底：

- **最多两行**，多写的丢掉。
- **单行夹到 40 字**（`OFFSCREEN_CHARS`），超了直接切——大事记是一行一条的硬事实，一条长文会常驻吃掉外场那 800 token 的预算。
- **前缀由引擎写**（`〔别处〕第 3 天·晚 `），不由模型写，同 `〔移动〕` / `〔日期〕` / `〔开场〕`。用「别处」不用「外场」：注入时那一整块的标题就叫【外场】，行内再挂一个同名标签等于说两遍。

### 写锁不跨 LLM 调用

`offscreen_brief` 拆成 读 → 关 → 调模型 → 开 → 写，结构同 `_settle` / `_maybe_summarize`；路由是在 `await db.commit()` **之后**才调它，回来再 `db.refresh(sess)` 把新写的大事记读回来——不刷的话玩家这一下看不到，下一轮却突然多出一条。整个函数不抛：简报没生成只是少一条传闻，时钟该走还是走。

### 验证

- 后端 **744 通过**（原 722）。
  - `test_rpg_schedule.py` 13 条：表内有值 / 表内没这个时段 / 空值 / 段名带空格 / `slot_locations` 是 `None` / 没有时段时作息表不参与 / 主角模板不算在场 / 被提到的人仍然注入。
  - `test_rpg_offscreen.py` 9 条：**开关关着时一次模型调用都没有**（路线级用一个「一碰就炸」的 patch 钉死）、没见过的人不进名单、名单为空不调模型、行带 `〔别处〕` + 天数 + 时段、模型说「无」就什么都不写、模型话多时夹到两行且单行截断、模型抛异常不拖垮时钟、**新写的大事记跟着同一次响应回去**。
- 迁移在**库副本**上试过（`sqlite3.backup()` 拷出来的副本，WAL 库直接 `cp` 会丢最近提交；真库只读打开）：两条 `ALTER` 第二次跑都会撞 `duplicate column name`，被 `_is_expected_migration_error` 吞掉；老行拿到 `slot_locations = '{}'`、`offscreen_brief = 0`。
- `tsc --noEmit` 干净，`vite build` 成功。**浏览器里没点过**——作息表那一栏、开场人物被禁用时的 title、按钮 title 的变化，都得真开一局看。

**明确没做**：让 NPC 自己决定去干什么（真正的自由行动）。那需要一套跨对话线的 NPC 状态 + 时段推进时的模拟。（下一章做了一个有界的版本：**打勾的角色会自己过日子，但不会挪窝**。）

## 二十六、AI 调度：没被提到的角色自己过日子（2026-09-12）

上一章解决的是「她在哪儿」，这一章解决的是**「她在那儿干什么」**。做法是**逐个角色打勾**：模组的角色卡上多一个「启用 AI 调度」，勾上的人在这一轮没被提到时，由模型替她记一句「最近在做什么」，玩家下回撞见她时带着这段日子。

选项 3 原先被搁置（用户要想想「是根据 AI 来还是什么」），最后落成的就是这个有界版本：**AI 来写，引擎来管边界。**

### 打勾而不是全局开关

一个模组里通常有一半的人（店老板、路人）根本不需要自己过日子，二十个人全开等于每轮都为名单上每一个人花钱。所以开关在**角色卡**上，默认关。

关着的模组行为和加这一章之前**逐字一致**：一次调用都不多。

### 存在局里，不写在角色卡上

`rpg_sessions.npc_activities`（`{"3": "在图书馆翻了一下午旧报纸"}`），键同 `npc_states` 是 `npc_id` 的字符串，值是**一句**话。

- **不写进 `rpg_npcs`**：同一个模组可以开好几局，写进卡里等于把 A 局的玩法带到 B 局——玩家在 B 局第一次见到赫敏，她已经在复述 A 局的事了。
- **不并进 `npc_notes`**：那张表是 GM 从这一轮叙事里**读出来**的近况（伤在哪、身上带着什么），这一句是调度**替不在场的人写**的行动。两个写手共用一套键名，模型迟早会用一个「伤势」盖掉刚记下的行动，而两边都以为对方在管——这正是当初把 `npc_notes` 从 `npc_states` 里分出来的理由。
- 一个角色**只有一句**，新的一次直接盖掉旧的。这是「最近」，不是日志；它每轮都要注入那个人的设定块。

### 谁算「没被提到」

判据是 `diag["npcs_onstage"]`（**在场 + 被名字或触发词提到**），勾了调度但不在这份名单里的才会被调度。

拿 `npcs_onstage` 而不是 `here_npcs`：模型上一轮在话里聊到了老兵，这一轮就不该再替老兵写一份——他这一轮归叙事模型管，两边各写一遍，玩家下回见到的会和自己刚经历的**对不上**。

**线主再补一笔**（`thread_id`）。模组一个地点都没定义时 `here_npcs` 恒为空，玩家在和她私聊、话里却没写她的名字，她就不在那份名单里——于是调度器会给一个**正在和你说话的人**另写一份「她今天在干什么」。

### 一次调用写完所有人

不是一人一次。勾了调度的角色可能有一屋子，一人一次的话玩家每轮要为 N 次往返付钱等时间。名单为空（都在场、或一个都没勾）时**直接返回，连模型都不叫**。

`rpg_activity.jinja2` 里逐条写死：名单里有几个人写几行、格式 `名字：做了什么`、只写他此刻所在地能发生的事、不许出现新的人名地名、不写对白、不写会改变玩家处境的重大事件、不许和「上次记下」那句逐字重复、没内容可写就不写。引擎侧兜底：名字用 `match_npc` 认（认不出就整行丢掉，**不报 warning**——这是玩家没要求过的后台动作），单行夹到 40 字（`ACTIVITY_CHARS`），「无」这类回绝不算数。

### 三件刻意不做的事

1. **不改 `location`。** 她在哪儿仍然只由作息表和常驻地点说了算。让模型顺手挪窝，玩家照着面板上的地点找过去就会扑空，地图的迷雾也无从跟着走。要让某人某时段换地方，用上一章的作息表。
2. **不写大事记。** 这是「她一个人干了什么」，不是「已经传开的事」。写进 `chronicle` 等于每条对话线上的所有人都知道了——大事记那条规矩禁的正是这个。
3. **不碰任何数值。** 数值归引擎，模型只能提议改动，这条是全模式的地基。

### 界面上把这条边界说出来（2026-09-12 补）

第 1 条「不改 `location`」有个副作用：**勾了调度的人，如果作息表和常驻地点都没填，她会永远站在玩家开局那个地方**，看起来就是「我勾了 AI 调度，她怎么还在这儿」，活像功能坏了。而这条边界在界面上原本一个字都没写——用户第一次撞上时只能猜（真库里的实例：赫敏常驻 `校长办公室`、作息表 `{}`、玩家也在 `校长办公室`，于是每一轮她都在场，连 `npc_activities` 也一直是空的，因为在场的人**不归调度管**）。

所以角色卡的「启用 AI 调度」下面多了一句黄字，只在勾了勾并且确实哪儿也去不了时出现，分三种：

- 模组没设时段 → 「她不会换地方——调度只替她写『在做什么』」。
- 作息表空着、常驻地有值 → 点名那个地名的，并告诉她去填作息表。
- 两样都空 → 说明白她在侧栏里根本不会出现（`npc_place` 返回空串，和谁都不等），并告诉她**把作息表每格填满就行，常驻地点可以一直空着**，嫌早/中/晚太粗就去「时段」里多写几格。

最后那句是针对一类角色的：**学生、行商这种没有固定落脚点的人**，最早那版提示写的是「先在上面填个常驻地点」——用户当场回了一句「赫敏是学生，没有常驻地点」。他是对的：`npc.location` 全仓只有一处功能读取（`npc_place` 的兜底，`rpg_context.py:135`；前端镜像 `condition.ts:76`），作息表填满之后它一次都不会被读到，是个纯替补栏。现在两处文案（调度提示 + 作息表说明）都改成了「常驻地点空着没关系」。

配套钉了两条测试（`test_rpg_schedule.py`）：作息表填满 + 常驻地点空 → 每格按表走；漏了一格 → 那一格 `npc_place` 返回空串（**不是**留在上一个时段的地方，作息表没有记忆），也就是那个时段她不在场。

顺带一句得让人知道的：**叙事可以让一个模型写「她摔门而去」，但面板不会跟着动**。地点永远只认字段，不认正文。



两个功能**挨着，但不是一回事**：

| | 外场简报（二十五章） | AI 调度（本章） |
|---|---|---|
| 开关在哪 | 模组上一个勾 | 角色卡上逐个勾 |
| 什么时候跑 | 只有**推时段**时 | **每一轮**（有人闲着就跑） |
| 写在哪 | 大事记，**跨线公开** | 这个人身上，**只有她的设定块看得到** |
| 内容 | 传进玩家耳朵的传闻 | 她自己过了什么日子 |

同时开两个不会打架（一个写公开栏、一个写私人栏），但**会各花各的钱**：推时段那一下会连着两次便宜调用。觉得重的话，作者留一个就行。

### 写锁不跨 LLM 调用 + 排在 done 之前

`idle_npc_activities` 拆成 读 → 关 → 调模型 → 开 → 写，结构同 `_settle` / `_maybe_summarize`。

**调用点在 `run_turn` 的最末尾、`yield "done"` 之前**，这是唯一一处「玩家说完话了还在调模型」：

- 它要知道这一轮提到了谁，那是 `build_rpg_messages` 算出来的，所以只能排在后面。
- 但必须排在 `done` 之前——`done` 之后前端不再收事件，只重新拉一次 session；排在 `done` 之后的话，玩家的侧栏会一直停在旧状态，下一轮才莫名多出一句。
- 代价要说清楚：**勾了角色的局，每轮叙事写完还要多等一次便宜模型的往返**。整个函数不抛，失败只是这一轮没记上。

### 玩家能划掉

角色详情里多一行「最近 · 在图书馆翻了一下午旧报纸」，悬停出「划掉」——路由 `DELETE /api/rpg/sessions/{id}/npc-activity/{npc_id}`，照 `delete_npc_note` 的做法（不拍存档：这是在改模型的笔误，不是剧情事件）。清理的是**这一句**，不是那个勾：勾是模组作者的决定，改它要回模组页。

`npc_activities` 也进了 `SNAPSHOT_FIELDS` / `SNAPSHOT_DEFAULTS`——和 `npc_notes` 同理，不回滚的话读档回来她还带着一句「未来」的行动。

## 二十七、模组设置页：改哪一格就存哪一格（2026-09-12）

二十六章修的那个「勾了 AI 调度，退出来又没了」，根子是**一页长到要滚好几屏的表单，而保存按钮孤零零挂在页头**。当时只在那一格旁边加了个「勾上立刻生效」的小标——治的是症状。这一章把根挖掉：**模组页上每一处改动都改完就自己进库，页头那个「保存」按钮撤掉了。**

原来的毛病不只是「忘了点」。同一个页面里本来就并存着两套规矩：「保存」管左栏那一大堆，而「开场人物」和子表（动作 / 道具 / 地点 / 词条开关）是当场落库的，旁边还写着「立刻生效，不用点保存」。两套规矩打架时，玩家只会记住更省事的那一条。

### 三个表单一个规矩

| 表单 | 以前 | 现在 |
|---|---|---|
| 模组本体（左栏全部 + 右栏参数） | 页头右上角「保存」 | 改完约 0.7 秒自动存 |
| 角色卡（编辑已有角色） | 表单底部「保存」 | 同上，底部多一个「收起」 |
| 世界书词条（编辑已有词条） | 表单底部「保存」 | 同上 |

**新建的那一行不自动存**：还没有 id，没得存。所以新角色 / 新词条仍然是「添加」，整份一起提交——AI 调度那个勾在新角色上也因此回到和其它栏一样的待遇。

### 页头那块换成状态条

原来的按钮位置现在只说一句话：`改动自动保存` / `保存中` / `已保存` / `没存上，点这里重试` / `模组名还空着，先不存`。

最后那一句是**必填栏空了**（模组的名字、角色的名字、词条的关键词和内容）。这时候**整份都不发**，而不是存一个空名字进去——空名字比没存更糟：它在列表上就是一行没有名字的东西，而用户只是把它清了准备重打。黄字说明为什么，改动留在表单里，不会丢。

**失败一定要说话**，这是二十六章那个坑的另一半：界面显示「已保存」而库里没有，比直接报错难查得多。存不上时状态条一直红着，点它重试；**收起表单之前也拦一道**——没存成就先不收，收了等于默默把改动扔掉。

### 这一发不能乱发

自动保存比「点一下保存」危险的地方在于它**发得多**。三件事在 `useAutosave` 里钉死：

1. **数据到位之前一个字都不发。** 表单是 `null` 起步的，早发一步就是拿一张空表单把整行盖掉。第一次看到真实值只记基准，不保存。
2. **同一时刻只放一个请求出去。** 打字期间会连着排好几次，而两个请求谁先落地并不由发出的顺序决定；后发的先到，库里留下的就是上一秒的旧值，界面上还看不出任何异常。所以有请求在路上时不另发，等它跑完再按**最新那一份**补一次。
3. **换行 / 收起 / 返回时把欠的那一次补上。** debounce 那几百毫秒是个真空档：改完立刻点「收起」、立刻点另一张卡、立刻返回列表，都会落在里面。所以 `startEdit` 先 flush 再换人，收起按钮先 `await flush()` 再关，卸载时也补一发。

配套的一条：**每份草稿自带它属于哪一行**（`{id, body}`）。收尾那一次是在表单已经换人、甚至已经关掉之后才跑的，`save` 闭包里的 `editingId` 那一刻早就不对了——id 跟着数据走，才不会写到新那一条身上。

### 顺手排掉的一颗雷

发出去的载荷是 `{...form}`，而 `form` 是 `RpgModuleOut` 的形状。以前这一发只发生在「点保存」那一下，现在每改一格都发，于是**同样一个毛病从「这次没存上」升级成「这一页从此一个字都存不进去」**。

拿两个 schema 对了一遍：`RpgModuleOut` 的 33 个字段里有 6 个（`id`、`updated_at`、`entry_count` 等）不在 Update schema 里，被 pydantic 忽略，无害；但 **`play_style` 是 `Literal`，老库里的空串会 422**。所以存回去的那一份统一过 `styleOf(form)` 兜成三选一——正好也是界面一直在显示的那个值。真库只读查过，两个模组都是合法值，这条暂时是保险而不是救火。

回写用 `qc.setQueryData` 而不是 `invalidateQueries`：这一发是拿表单当真的，重取一次反而会拿服务端那一份把用户正在敲的字盖回去。同理，表单只在**换模组**时灌一次（`hydrated` ref），不再跟着 `module` 变就灌。

### 一个副作用，用的人得知道

「帮我写」生成的那段草稿，点「用这段」写进表单之后**也会在一秒内落库**，不再有「先看看、先不保存」这个环节。要反悔就再改回去。这是「改了就存」的固有代价，不是 bug。

### 验证

- `tsc --noEmit` 干净，`vite build` 成功。
- 载荷对过 schema（不碰任何库）：原样发、`play_style` 为空串时确实 422，兜底之后 27 个真字段进路由、6 个多余键被忽略。
- 真库只读查了一遍 `play_style`：两个模组（`sim` / `rpg`）都合法。

**没测的**：这一章全是前端行为，而这个仓库没有前端测试框架（`tsc` + `vite build` 是仅有的两道闸），所以**一次浏览器都没点过**。要手点的：改一格看页头从「保存中」变「已保存」；把模组名清空，看状态条变黄且改动留在框里；把后端停掉改一格，看它变红、点得动、恢复后再点能存上；改完立刻点返回，再进来刷新看改动还在；编辑 A 之后立刻点 B，回头看 A 的改动没丢。

**明确没做**：关标签页之前那 0.7 秒里的改动会丢。要救得走 `sendBeacon` / `keepalive`，那是另一条路，这一轮不铺。

## 二十八、剧情把人挪走：玩家说「你过来」，她就真的过来（2026-09-12）

起因是一句追问：「晚上她作息是宿舍，主角把她叫到校长办公室，该怎么算？」

### 旧行为是什么

「在哪儿」只有两个来源：作息表 → 常驻地点，都是**静态字段**。所以「你过来」这句话引擎听不懂：

| 环节 | 旧行为 |
|---|---|
| 这一轮的提示词 | 她在（注入口径是「在场 ∪ 被提到」，她那句话里有名字） |
| 侧栏她那一行 | 还写「宿舍」，不说「就在你面前」 |
| 再聊两三句 | 名字滑出扫描窗口（默认往回扫 2 条），她整轮掉出提示词，正文里却还站在办公室里 |
| 单独找她说话 | 开不了：`thread_blocker` 看字段，线主不在跟前整轮拒成 400 |
| AI 调度 | 开始替她写「在宿舍干什么」，和正文互相打脸 |

### 根子：玩家自己的位置**本来就是模型写的**

`apply_state_delta` 里 `location = delta["location"]` 直接落库、顺手 `note_visited` 记地图迷雾——**模型每轮都在提议玩家去了哪儿**，连地点表都不查。所以「模型提位置 → 后端落库」这条管道早就在跑，给 NPC 加一个只是**同一个 JSON 里多一个键**，同一次调用、零新增开销。当初「模型不许挪人」那条规矩管的是 **AI 调度**（它看不到剧情，挪人就是凭空），不是结算。

### 现在的取值链

```
这一局的 npc_places（剧情）  →  作息表  →  常驻地点
```

- 新列 `rpg_sessions.npc_places JSON DEFAULT '{}'`，键是 npc_id 的字符串（同 `npc_states`），值是地名。
- 唯一读取点仍然只有 `rpg_context.npc_place`（后端 5 处、前端镜像 `condition.npcPlace` 3 处调用全部一起改）。谁在场仍然只有 `here_npcs` 一种问法。
- 写回走结算：`_settle` 提示词末尾追加一段「人物位置」，模型在输出里带 `npc_places`，`apply_state_delta` 夹紧后落库。
- 空串 = 清掉这一格，她回到作息表安排的地方（「你回宿舍去吧」就是这条路）。

### 三道闸

1. **可动的人 = 刚写出的正文里真的出现过的人**（`named_npcs`）。比「被提到」再紧一层：玩家嘴上抱怨一句马尔福，不该把马尔福挪到他跟前；正文写了他推门进来才算。提示词里那份名单和写入时的闸门**是同一条规则**，两边不能分叉。
2. **私聊线里不动位置**，和玩家位置共用 `allow_move` 那一个开关，理由一字不差：角色线里线主被叙述走开，她那条线的输入框就永久置灰了。
3. **推时段清空整张表**。时段一变作息表重新说了算，否则模型随手一笔会永久盖掉作者排的作息表。

调度那条规矩**没变**：`idle_npc_activities` 仍然一个字都不许挪人。

### 「让她离开」时她去哪

由模型写，不是系统猜：写地名就去那儿；写空串就按上面那条链回落，**两个都空就是「行踪不明」**（侧栏照实这么显示，`NpcSheet` 写「行踪不定」）。所以给没有固定落脚点的角色（学生）**把作息表每一格填满**，等于给「回去」这个词一个确切的含义——常驻地点仍然可以空着。真出现「哪儿都不是」的局面，补一句「你回宿舍去」就有地方了。

### 提示词为什么不写进 `rpg_settle.jinja2`

那个模板用户可以自定义，往里加变量会让存过旧版本的人静默失效（同 `style_block` 的理由）。所以这一段是 Python 拼在模板**后面**的（`_place_block`），自带字段说明。

### 验证

- 后端 806 条全绿，其中新增 36 条（`tests/test_rpg_npc_place.py`）：取值优先级、清空回落、允许名单、私聊线拒绝、非字典载荷不炸、`advance_slot` 复位、快照字段，以及**整条线跑一遍**的三条（提示词里出现「赫敏 现在在 宿舍」、模型写回来落库、并进了发给前端的那份状态）。
- 迁移在**库副本**上演练（`sqlite3.backup()` 拷的，真库只读打开）：先 `DROP COLUMN` 造出「第一次」的局面，跑两遍 `init_db()`——第一遍 ALTER 成功、第二遍被「列已存在」吞掉，老存档拿到 `'{}'`。
- 注意：真库上这一列**在演练之前就已经有了**——开发服务器带 reload，改完 `models/rpg.py` 它自己跑了一遍 `init_db()`。这是它本来的行为，ALTER 只加列、带默认值，没有覆写任何数据。

**没测的**：浏览器一次都没点过（这个仓库没有前端测试框架）。要手点的：开一局，跟赫敏说「你过来」，看侧栏那一行变「就在你面前」、能不能点开她的私聊线；再说「你回宿舍去」，看它变回「宿舍」；按一下「结束这个时段」，看临时位置被清掉、作息表重新说了算。

## 附：模组构思向导

对话式生成整套模组数据，回填到模组编辑页。方案全文见 `docs/RPG模组构思向导.md`。

五步：世界观 → 数值 → 地点 → 角色 → 道具动作。顺序有依赖，不能调。

**为什么分步抽取、不能像小说侧那样全量重抽**：RPG 的数据靠名字互相引用——角色的
关系数值起点引用关系数值名、道具/动作的 effects 引用玩家数值名、角色的所在地点
引用地点名。全量重抽会让后面的步骤把前面定好的数值表重抽一遍，「精力」抽成
「体力」，于是道具点下去静默失效、不报错。所以每步只抽自己那一摊，前面已定的名字
当白名单传给后面的步骤，`rpg_wizard.extract_stage` 抽完按白名单过滤，丢掉的进
`dropped` 显示给作者。

**校验责任**：后端只按「聊定那一刻的白名单」过滤。前端预览面板（`WizardApplyModal`）
再做一次活的引用校验——作者取消勾选某个数值后，引用它的道具就悬空了，那是后端
拦不到的，当场提示。

**回填顺序**：地点 → 角色 → 道具动作，理由同抽取顺序。全在 `RpgModule.applyWizard`。

代码位置：后端 `agents/rpg_wizard.py`、`prompts/templates/rpg_wizard*.jinja2`、
`api/routes/rpg.py` 的 `/modules/{id}/wizard[/extract]`；前端 `pages/Rpg/WizardPanel.tsx`、
`WizardApplyModal.tsx`、`wizardStages.ts`。测试 `backend/tests/test_rpg_wizard.py`。

SSE 的 `stream_chat` 从 `chat.py` 提到了 `services/sse.py`，小说侧和 RPG 侧共用。
