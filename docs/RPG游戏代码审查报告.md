# RPG 游戏代码审查报告（2026-09-20）

一次从头到尾的全面审查，覆盖五件事：角色上下文是否独立、玩家信息是否对 NPC 隔离、移动判断支持哪些说法、时间天数怎么进上下文、有哪些冗余代码。每条结论都给了代码位置，可以直接点过去核对。

**先说总体结论**：前四件事的架构是健康的，隔离和移动识别都做得比预想扎实，靠的是"结构挡住"而不是"提示词嘱咐"。真正的问题集中在几个点上：新的分角色管线把 NPC 的"活状态"（关系数值、近况、经历、说话样例）留在了一个再也不写台词的 GM 手里；移动的 AI 兜底已经名存实亡但注释还说它在；外加一簇从没接上线的死功能（NPC 留言）。下面分五节说。

---

## 一、角色上下文是不是单独的

**结论：是，而且是两层。** 比要求的"单独记录"做得更深。

### 第一层：记忆格子（每个角色一格）

每条消息落库时带一个 `present` 快照（当时谁在场）。读记忆时按"格子"分：玩家一格、每个 NPC 一格（`rpg_context.py` 的 `message_slots`，1128 行）。一条消息进哪些格子的规则是：

| 情况 | 进谁的格子 | 代码依据 |
|---|---|---|
| 私聊 | 玩家格 + 只有对面那一个人的格 | `turn_present` 私聊收窄（rpg_context.py:375）；路由写 present 用同一个函数（routes/rpg.py:2220） |
| 群聊 | 玩家格 + 在场每个人的格 | `present_ids`（rpg_context.py:353） |
| 独自行动 | 玩家格 + 在场旁观者的格 | 刻意设计："独自行动不等于没人看见"，她看着你翻出剑谱，下一轮就该知道你有（rpg_context.py:375 注释） |
| AI 调度的经历 | 写进 `npc_activities`（最近在做什么）和 `npc_history`（只追加的经历流水） | rpg_turn.py `idle_npc_activities`；结算写 npc_history（rpg_settlement.py:1145） |
| 角色自己的信息 | 角色卡（简介/人设/外貌/档案）+ 关系数值 + 眼下近况 | `_one_npc`（rpg_context.py:761） |

每个格子有自己的"最近 N 条 + 自己的概要"，压缩也按格子各压各的（rpg_turn.py `_maybe_summarize`），发原文和压概要用同一个筛选函数 `slot_window`，两边不会分叉。

### 第二层：知情管线（~~这次改动新加的，比格子更硬~~ **已于 2026-09-20 撤回，主线不再跑**）

> **撤回说明**：这套管线一轮要发 **3+N 次**模型调用（GM 写草稿 → 感知分发 → 每个 NPC 各一次 → 合稿），正文实际被生成三遍（草稿、分发时逐字重抄、合稿重写），演员那几次还走写作模型且串行；更要命的是整条链路攒到最后才吐字，玩家盯着空白等全部跑完。生成明显变慢、token 成本翻了几倍，所以 2026-09-20 换回"一次注入全部上下文、单次流式生成"的老路（rpg_turn.py:2128 起，与小说侧 `stream_chapter` 同形状），隔离改由提示词约束承担——见第二节。
>
> 代码连同两个测试文件存档在 `rpg-knowledge-pipeline` 分支（commit 411cf0a，1188 行，本地未推送），`git show rpg-knowledge-pipeline:backend/app/services/rpg_knowledge.py` 可取回。
>
> **本节以下两段、以及紧跟着的"问题 1"，描述的都是这套已撤回的管线**，留作设计记录，别当成当前实现读。下面的"问题 2"讲的是第一层（格子），仍然有效。

`rpg_knowledge.py` 实现了"分角色生成"：GM 只写环境草稿（明令禁止写任何 NPC 台词和反应）；一个"感知分发器"把草稿和玩家输入切成逐字片段，逐条标注"谁听见了/看见了"；然后**每个 NPC 用单独的一次模型调用**回话，它的输入只有：自己的角色卡（人设/外貌/背景故事/能力特长）、分给它的感知片段、以及历史上标注过它是听众的记忆条目。它压根拿不到 GM 的完整上下文。

这套东西有整整两个测试文件兜底（`test_rpg_knowledge.py`、`test_rpg_knowledge_turn.py`），包括"演员拿不到玩家面板"、"同屋不等于知道私事"、"演员失败不许退回全知草稿"等边界。

### 发现的问题

**⚠ 问题 1（本次审查最重要的发现）：NPC 的"活状态"没跟着搬进演员的输入。**

> **注：本条已于 2026-09-20 修掉**，下面这段是修之前的原貌，留作背景；修了什么见文末行动清单第 1 条。
演员模型的 payload（rpg_knowledge.py:421 `actor_messages`）只有人设、外貌、背景故事、能力特长。以下东西它一概看不到：

- **关系数值**（好感 62/100）——这是"数值驱动"模式的核心。它只在 GM 的角色卡里（rpg_context.py:794），而 GM 现在被 SCENE_INSTRUCTION 禁止写 NPC 的台词和反应。也就是说：**好感涨到 90 和停在 10，NPC 说话的态度可能没有任何区别**，因为决定它态度的那个模型看不见这个数。
- **眼下近况**（npc_notes：她左肩还在流血）
- **最近在做什么**（npc_activities，AI 调度写的）
- **经历流水**（npc_history）——只能靠感知记忆间接覆盖，调度写的那部分覆盖不到
- **说话样例**（dialogue_examples）——作者写的语气示范现在影响不到台词

测试名 `test_actor_does_not_receive_player_sheet_summaries_or_relationship_network` 说明这是刻意的（防泄漏），但"防玩家底细泄漏"和"角色自己的关系数值、自己的语气"是两码事，后者被一刀切掉了。**后续版本要么把这几样安全的东西（它自己的关系数值、自己的 notes/activity、自己的说话样例）补进演员 payload，要么明确接受"关系数值只影响条件门槛、不影响语气"这个降级。**

**问题 2：没建任何地点的模组 = 所有人全程在场。** `present_ids` 的兜底是"没有地点就全员在场"（rpg_context.py:353 注释）。纯对话模组里这是必要的，但后果是：这类模组里玩家的每一轮（包括独自行动）都会进所有 NPC 的格子和知情记录，隔离等于不存在。这是已知取舍，写在这里备查。

## 二、玩家信息（任务/道具/技能/数值/独自行动）对 NPC 的隔离

**结论（2026-09-20 改写）：仍然达标，但不再是双保险——硬的那一层随知情管线一起撤回了，现在挡在正面的只有提示词，外加长期记忆这一层兜底。**

~~**演员层（硬隔离，结构挡住）**~~ **已随管线撤回（2026-09-20）**。它当时挡的是：写 NPC 台词的模型输入里根本没有玩家的任务、道具、技能、数值；感知分发器明文禁止分发"玩家心理、计划、没有展示的背包、没有说出口的任务"（rpg_knowledge.py:44 `PERCEPTION_INSTRUCTION`），且每个片段必须原文逐字引用、模型编不出来；独自行动时玩家输入不算"说出口的话"（`test_solo_input_is_not_treated_as_spoken`）。这些代码现在只在 `rpg-knowledge-pipeline` 分支上。**撤回的代价就是这一层**——权衡见一节的撤回说明。

**提示词层（软约束，现在唯一的正面闸）**：一轮只有一次调用，它的 system 里必然有整份玩家面板（要判断"这事做不做得成"），而同一个模型同时在写屋里所有人的嘴——泄漏与否完全取决于它听不听话。四处约束：

- `PRIVATE_SHEET_NOTE`（rpg_context.py:107）——"这是他的底细，除非亲眼见过/他说过/事是那人交代的"，贴在【你】段抬头后面而不是末尾，因为超预算时是从尾巴上切
- `SCENE_PREAMBLE`（rpg_context.py:185）——"在场的人只知道自己也在场的事，不要让他们主动提起"
- rpg_gm.jinja2 第 26 行——"不要让 NPC 张口就知道玩家的背包、技能和手上的事"，并列出三个口子（见过/说过/他交代的）
- `_scene_line`（rpg_context.py:505）——把玩家明选的模式写进提示词："你在做自己的事，没有在跟谁说话；X 在旁边看着"。挡的是"选了独自行动，旁边那位照样搭话"

另有 rpg_gm.jinja2 第 14 行"在场名单之外的角色不得出现在本轮场景里"（撤回时从 `SCENE_INSTRUCTION` 捞回来的，见行动清单第 3 条）。

**这一层的性质要说清楚**：软约束会被破例，而结构隔离不会。要把可靠性拉回来，方向是**事后校验**（正文里出现玩家没展示过的道具名/任务名就打回或标记），不是把 3+N 次调用的管线搬回来。

**长期记忆层**：结算出的事实带 `witnesses`（见证人）名单，写入时收得很紧——私聊事件的见证人只认出发时在场名单，"公开"必须正文明写传播词（传开/公告/人尽皆知，rpg_settlement.py:660）。回忆检索时，非公开事实要求"本轮全部听众都是见证人"才放行（rpg_memory.py:66）；没结算过的原文更严，要求听众全在当时的 present 里（rpg_memory.py:90）。

**一处已知天花板**（代码里自己标了 ponytail，rpg_memory.py:86-88）：消息本身没有 visibility 字段，所以"玩家独自经历的往事"在 NPC 在场时连 GM 的回忆块都进不来——方向是过严而不是泄漏，安全但可能让 GM 忘事。升级路径注释里写了（给消息补 visibility）。

**几个"看起来像泄漏、其实是设计"的点，别当 bug 修**：
- 独自行动时在场 NPC 能"看见"你的可见动作——设计如此，否则出现"她亲眼看着你翻剑谱、下一轮却不知道你有"的失忆镜像 bug。
- 大事记【外场】全员可见——它的定义就是"已经传开的事"，抬头话术明确"听说不等于亲眼见过"。
- GM 能看到隐藏数值（display=隐藏）——隐藏只是不给玩家看，GM 得知道怀疑度 80 了会怎样。

## 三、地点移动的判断

**结论：三种场景都支持，识别是一套"宁可漏认、绝不错认"的正则引擎。两个误移动 bug 已于 2026-09-20 修掉，剩下一个名存实亡的兜底。**

### 机制概览（三层）

1. **入口识别**（纯代码正则，routes/rpg.py:2177 → rpg_turn.py `parse_company` / `movement_target`）：从自由输入里认出"玩家去哪 / 带谁 / 派谁 / 打发谁"。另有地点总览的**瞬移按钮**（零模型调用，`move_by_name`）。
2. **引擎落库**（确定性）：查登记地点表 → 过 `enter_requires` 门槛 → 写 `sess.location` + 大事记 + 地图迷雾 + 消息快照。**不看 connections**（连接只画地图，不拦路）。
3. **AI 结算**：只能挪 NPC（npc_places，且只许挪正文里露过面的人、只准填登记地名）；**玩家位置被引擎锁死**——每轮的 `fixed_location` 会让结算里的 location 提议直接被丢掉（rpg_settlement.py:897）。

### 支持的句式清单

**(a) 玩家自己移动** —— 移动动词表：`前往|前去|去往|走到|走向|走进|进入|回到|返回|回|移动到|赶往|来到|去`（rpg_turn.py:502）。支持：光打地名（"灵药园"）、动词+地名+要干的事（"去酒馆买酒"，尾词白名单）、尾段简称（登记"灵药园柴房"、嘴上说"柴房"）、提议句（"要不我们去酒馆吧"）。拒绝：问句、否定（只看动词前 4 字窗口）、他人主语、未登记地名、一句两个目的地（交回 AI）。

**(b) 指定角色移动** —— 两种句式：使役动词式"派/让/叫/吩咐/命令 + 人 + 去 + 地名"；句首裸主语式"赫敏去客栈"（主语必须精确全名，防"我看见赫敏"误伤）。落库写 npc_places 并自动解除她的跟随。前提：人必须在场、地名必须登记过、代词"你"只在跟前恰好一人（或私聊）时认。

**(c) 带角色一起移动** —— 四种句式：携带动词"带上/领着/叫上/拉着…+人"；"和/与/同 + 人 + **一起**"（必须有"一起/一块/俩"尾巴）；"我们/咱们"= 屋里全员；"你跟着我"。落库只写 `npc_followers` 名单、**不写位置**——跟着的人的位置由 `npc_place` 取值链当场算出来（跟随 = 玩家在哪她在哪，零写入），架构上不存在"带人走只更新了玩家"的经典漏洞。解除跟随："别跟着了 / 你回去吧 / 都散了"——打发式的"走吧 / 回去吧"只在**没说去哪儿**时算打发人，"走吧，去密室"是招呼着一起动身（rpg_turn.py:1133）。

### 发现的问题（按重要性排）

1. **"认不出就交给 AI"的移动兜底是死路。** 注释和测试文档都说"漏认不致命，整句交回 AI 结算"，但 `fixed_location` 每轮都锁（rpg_turn.py:1950），结算的 location 提议无条件被丢（rpg_settlement.py:897）。所以正则认不出的移动说法，玩家**根本走不了**，最多收到一条"剧情抵达 X 与引擎地点冲突"的复查提示。要么修注释认账（"移动只认引擎"），要么给结算开一条受核查的口子。
2. ~~**两个测试里自己钉住的误移动 bug**：①"派赫敏去客栈"而赫敏不在场时，派遣认不出、回落到移动识别，把**玩家自己**挪去了客栈；②"我看见赫敏去客栈"这类陈述句同样会把玩家挪走。~~ **已修（2026-09-20）**：① `_moves_by_someone_else`（rpg_turn.py:1055）按分句判"这句里动身的是不是别人"，认出来就整句交回 AI，绝不落到 `movement_target`；② 感知和转述动词（看见/听说/得知/告诉/以为…）并进了 `_MOVE_DENY`（rpg_turn.py:515），裸"说"刻意不收（会误杀"跟掌柜说一声再去酒馆"）。两条钉 bug 的测试已翻面：test_rpg_follow.py:423、:550，外加 test_rpg_movement.py `PerceptionWordingTests`。
3. **"我和艾拉去森林"（没说"一起"）只动玩家、不带人。** 刻意取舍（防"我和他不一样"误命中），但这是"一起移动"最常见的口语之一，属于部分支持，值得在界面或文档里提示玩家。
4. **私聊模式下玩家不能自由移动**——**这条已部分过期**：明说自己要走（"你前往灵药园。"）现在照走，认出来就当场散场按群聊走（test_rpg_movement.py:335）。仍然被丢弃的只有 `move_to` 这个字段（地点总览的瞬移按钮），有意设计但没有任何提示。
5. **同名地点**：两个完全同名的登记地点会被折叠成一个，取的是第一个的进入条件——低概率但存在。
6. **派遣不查 enter_requires**：NPC 可以被派进玩家自己进不去的地点。设计意图不明（enter_requires 可能本来就只管玩家），代码里没有注释说明，建议补一句注释定死口径。

## 四、时间天数的注入

**结论：注入是合理的，位置和层次都对，没有发现漏注或错注。** 时间只有一个写入源（引擎的 `advance_slot`，rpg_state.py:1502：时段走完一圈 → 天数 +1 → 跨天恢复七成），模型永远只是读者。

### 注入到哪几块

| 注入点 | 内容 | 条件 |
|---|---|---|
| GM system 的【你】段 | `时间：第 N 天 · 时段` | 模组设了时段才有（rpg_context.py:593）；开局就会站上第一格（routes/rpg.py:991），所以设了时段就不会空 |
| GM system 末尾的场景锚 | `当前时间 / 本轮行动结束时间：第 N 天 · 时段` | 同上（rpg_context.py:1065） |
| 玩家那句话的最前面 | 推过时段后的那一轮贴【时间已推进·不可忽略】块，说完即清；带行动耗时的贴起止时间块 | `time_jump_block`（rpg_context.py:1076），刻意不放 system——离对话越近越不会被无视 |
| ~~NPC 演员的 scene~~ | ~~`{day, slot, turn}`，给记忆里的 when 当参照系~~ | **已随管线撤回**（原 rpg_knowledge.py:451） |
| 记忆条目 | 每条带 `when`（第 N 天·时段·第 N 回合），时间戳是引擎写入那一刻盖的，不是模型填的 | `_when`（rpg_context.py:729）；~~`when_of`（rpg_knowledge.py:138）~~ 已随管线撤回 |
| 大事记 / 经历 / 里程碑 | 每行带"第 N 天·时段"前缀；跨天时写一条"第 N 天开始了" | rpg_state.py:1394、:1556 |
| 外场简报 / AI 调度提示词 | day、slot 变量 | rpg_turn.py:1540、:1744 |

### 为什么说合理

- **没设时段的模组，天数永远是 1 且永不显示**——这是自洽的：时钟不存在，显示"第 1 天"只会诱导模型自己编"不知不觉天黑了"（rpg_gm.jinja2 第 14 行明令禁止），而 rpg_gm 也交代了"没有时间推进信息时维持当前时段"。
- **时间跳跃块放在玩家消息前而不是 system**，注释讲得很清楚：推时段不产生对话消息，模型眼前是"上一幕长文 + 玩家下一句"，天然读成无缝衔接，system 末尾一句提示压不过整段深夜正文。
- **记忆带时间戳解决了"旧事重演"**：玩家送出去的东西，NPC 不会隔几回合又重新接一次（ACTOR_INSTRUCTION 里明确"when 和现在对不上的是过去的事，不要再演一遍"）。

唯一可挑剔的小点：裁决提示词（rpg_adjudicate）里没有时间——但裁决只判难度档位，用不上时间，不算缺口。
